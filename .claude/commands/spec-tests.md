# 作成済みの仕様からテストを作る

目的は、`specs/` に既にある仕様の項目（受け入れシナリオ・境界値・成功基準）ごとに、GoogleTest を 1 本ずつそろえること。
新しいプロジェクトでも既存のプロジェクトでも、`/gtest-setup` の後はこの手順でテストをそろえ、そのあと `/coverage` で抜けを埋める。

入力: $ARGUMENTS（機能番号。無ければ手順 1 の一覧を出して止まる）

## 手順

1. **一覧を作る**: `specs/*/spec.md` をすべて読み、機能ごとに次を数えて表にする。
   - 仕様の項目: 受け入れシナリオ（AC-001 などの ID。ID が無い古い仕様は `US<ストーリー番号>-<シナリオ番号>` と呼ぶ）、境界値（B-01 など）、成功基準（SC-001 など）
   - テスト済み: `tests/` の中で、テスト名 `F<機能番号>_<ID>_...` か `RecordProperty("spec", "<機能番号>:<ID>")` が見つかる項目
   - 表: `機能 | 項目数 | テスト済み | 未テスト | GUI・手動のみ`
   - `specs/` が無い、または仕様が 1 つも無いときは「作成済みの仕様はありません。/speckit-specify から始めてください」と伝えて止まる。
   - $ARGUMENTS が無いときは、表と「始めるのにおすすめの機能」（画面に依存しないロジックが多く、未テストが多いもの）を示して、どれから始めるかを聞いて止まる。
2. **1 機能ずつ読む**（$ARGUMENTS の機能だけ。複数あれば番号順に 1 つずつ）: `spec.md`、同じフォルダーの `data-model.md`・`contracts/`、対象の関数を宣言しているヘッダーを読む。仕様の項目ごとに、次のどれかに分ける。
   - **テストする**: 期待値が仕様から決まり、画面を使わずに呼べる
   - **GUI・手動のみ**: 画面の操作や見た目でしか確かめられない → テストは書かず、報告に理由を書く
   - **期待値が決まらない**: 仕様の書き方があいまい → テストは書かず、報告で人に質問する
3. **テストを書く**（「テストする」項目だけ）:
   - 置き場所: `tests/unit/feature_<機能番号>_spec_tests.cpp`（既にその機能のテストのファイルがあれば、そこに足す）。新しいファイルは `tests/CMakeLists.txt` の `add_gtest` に `unit` で登録する。
   - 1 項目 = 1 テスト。境界値の表は `TEST_P` で 1 行 1 ケースにする。
   - テスト名は `F<機能番号>_<ID>_<条件>_<結果>`（**英数字と _ だけ**。日本語にすると ctest で 0 件実行のまま成功になる）。`RecordProperty("spec", "<機能番号>:<ID>")` を付ける。
   - 各テストの直前のコメントに、根拠（ファイル名と節や ID）を日本語で書く。アサーションのメッセージも日本語。
   - 期待値は仕様から書く。今の実装を動かして出た値を、そのまま期待値にしない。
4. **ビルドとテスト**: `cmake --build build --config Debug` と `ctest --test-dir build -C Debug --output-on-failure -LE slow` を実行する。
   - 新しいテストが失敗したら、**仕様と実装の食い違い**。期待値も製品のコードも変えない。そのテストの先頭に `GTEST_SKIP() << "仕様と実装の食い違い（人の判断待ち）: <内容>";` を入れて、テスト自体は残し、報告に載せる（人が「実装を直す」か「仕様を直す」かを決める）。
   - ビルドの失敗や、既にあったテストの失敗は、先に原因を調べて報告する（テストは消さない）。
5. 次の機能があれば 2 に戻る。終わったら報告し、「続けて /coverage で抜けを埋められます」と伝える。

## 終わりの報告

短く、次の順で書く。
1. 結果: 機能ごとの `項目数 | テストを足した数 | GUI・手動のみ | 質問 | 食い違い`、ctest の結果（件数）
2. 足したテスト: `ID | テスト名 | 根拠` の表
3. 食い違い（GTEST_SKIP にしたもの）: `ID | 仕様の期待 | 実装の動き | テスト名` の表
4. 質問（期待値が決まらない項目）: `ID | 仕様の文 | 何が決まっていないか`
5. GUI・手動のみ: `ID | 理由`

## してはいけないこと

- 仕様に無い動きのテストを書くこと（それは /coverage で人に確認する）
- 製品のコードや仕様（spec.md など）を変えること（食い違いや不具合は報告だけする）
- 既にあるテストを消す・期待値を緩めること
- 食い違いのテストを、人が決める前に消したり、期待値を実装に合わせたりすること
- $ARGUMENTS が無いのに、全機能のテストを一度に書き始めること
