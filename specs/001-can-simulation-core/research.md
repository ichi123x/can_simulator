# Phase 0 Research: CAN バスシミュレーション コア機能

`spec.md` の Assumptions で「設定ファイルの形式」「ログの出力形式」を実装詳細として`/speckit.plan` 以降に委ねていたため、本フェーズでこれらと関連する技術選定を決定する。

## 1. 設定ファイルの形式

- **Decision**: 外部ライブラリに依存しない、セクション区切り＋ `key=value` の軽量独自テキスト形式とする（例: `[Node1]` セクションの下に `Name=`, `RxFilter=` 等、フレームは`[Node1.Frame1]` のように ID・DLC・データ・周期・初回オフセットを列挙）。
- **Rationale**: リポジトリには vcpkg/NuGet 等の依存関係管理が一切導入されておらず（`.vcxproj` に外部パッケージ参照なし）、JSON/YAML パーサを追加すると新規の外部依存という複雑さが生じ、憲章 IV（シンプルさ優先・YAGNI）に反する。Win32 API 標準の `GetPrivateProfileString`系（INIファイル読み込み）は Unicode パス・大きな値の扱いに制約があるため、代わりに STL の`<fstream>` のみで読み書きできる自前パーサを採用する。
- **Alternatives considered**:
  - JSON（nlohmann/json 等）: 表現力は高いが、新規依存関係の導入とパッケージ管理の整備が必要になり、現状の「依存関係管理なし」という前提を崩す。
  - Windows INI (`GetPrivateProfileString`): 追加依存は不要だが、フレーム一覧のような繰り返し構造の表現が不自然になり、DLC分のデータ列（可変長バイト列）を素直に書けない。
  - CSV 一本化: ノード属性とフレーム一覧で列構成が大きく異なり、1ファイルに混在させると可読性が落ちる。

## 2. ログ出力形式

- **Decision**: CSV（UTF-8、ヘッダ行あり）を必須形式とする。JSON Lines 出力は本フェーズのスコープに含めない（必要になった時点で別機能として追加）。
- **Rationale**: ドメイン仕様書（`Doc/CANバスシミュレータ仕様.md` FR-052, FR-054 のログ例）がCSV を基本形式として例示しており、`spec.md` の FR-017 が要求するログ項目は CSV の1行1レコードで過不足なく表現できる。JSON Lines は「[要確認 Q-6]」として仕様書側でも任意扱いであり、今使う具体的な要求がないため、憲章 IV（YAGNI）に従い初期版では実装しない。
- **Alternatives considered**:
  - CSV + JSON Lines 両対応: 将来的な柔軟性はあるが、初期版で使われる見込みが薄く、実装・テスト対象が倍になる。
  - JSON Lines のみ: 表計算ソフトでの確認（ドメイン仕様書のログ例がCSV前提）と相性が悪い。

## 3. 自動テスト基盤

- **Decision**: 本フェーズでは新しい自動テストフレームワーク・専用 VS プロジェクトを導入しない。`CanSim/` 配下のクラスを `CDialogEx` から独立したプレーン C++ として実装することで、将来テストプロジェクトを追加する際の障壁をなくす（分離のみを今回のスコープとする）。
- **Rationale**: 憲章 III は「UI から分離可能な形で実装する」ことを要求しているが、テストフレームワーク自体の導入を義務付けていない。現状リポジトリにテスト基盤が一切なく、本機能1件のためだけに（例えば）Google Test 等を導入すると、ビルド設定・CI 不在の状態で管理コストが見合わない（憲章 IV）。検証は `quickstart.md` の手動シナリオで代替する。
- **Alternatives considered**:
  - Google Test / Catch2 導入: 将来的には望ましいが、依存関係管理の整備（研究1参照）と合わせて別途スコープとすべき規模の変更になる。
  - MSTest (Native Unit Test Project): Visual Studio 標準で追加依存は不要だが、新しい VSプロジェクトの追加が必要になり、Project Structure をシンプルに保つ方針と衝突する。

- **その後の改定（2026-09-28、機能 002 完了後）**: 検証に使っていた `cl.exe` 直接ビルドのハーネスを、スクラッチ領域から `tools/cansim_runner/` へ移してリポジトリに含めることにした（複数の作業マシンで同じ検証を再実行できるようにするため）。本決定の主旨は変えていない: `MFCApplication1.sln` にテストプロジェクトは追加せず、外部のテストフレームワークも導入していない。`tools/cansim_runner/` は手動でビルドして使う開発補助ツールであり、ビルド手順は憲章 III の要求どおり CLAUDE.md に記載済み。

## 4. 性能目標（暫定値）

- **Decision**: 既定構成（6ノード・500 kbps、付録A相当）で10秒間のシミュレーションを1秒未満で完了することを暫定の性能目標とする。
- **Rationale**: ドメイン仕様書の SC-006 は「性能目標は実行環境が決まってから設定する（Q-8 未決）」としているため確定値がない。一方で `plan.md` の Technical Context は空欄ではなくデフォルトを持つべきであり、イベント駆動シミュレーションはビット単位シミュレーションより大幅に軽量なため、この程度の余裕あるデフォルトは現実的である。Q-8 が確定した時点で`/speckit.constitution` または本機能の `spec.md` 更新を通じて正式な数値に置き換える。
- **Alternatives considered**:
  - 目標値を設定しない（NEEDS CLARIFICATION のまま残す）: `/speckit.plan` は「すべてのNEEDS CLARIFICATION を解消する」ことが求められているため不採用。

## まとめ

すべての `NEEDS CLARIFICATION` は本ドキュメントで解消済み。Technical Context に残る未確定はない。
