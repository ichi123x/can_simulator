# Quickstart: CAN バスシミュレーション コア機能の検証

`spec.md` の User Story 1〜3 が満たされていることを手動で確認するための最小手順。自動テスト
基盤は本フェーズで導入しない（`research.md` 決定3）ため、実装後はここに記載した手順で確認する。

## 前提

- `MFCApplication1.sln` を Debug / x64（または Win32）でビルド済みであること。
- 動作確認用の設定ファイルとして、ドメイン仕様書 付録A 相当（6ノード・8フレーム、500 kbps）
  を `contracts/config-input-format.md` の形式で用意する。うち ECU3（0x080, 周期10ms）と
  ECU1（0x100, 周期10ms）の初回オフセットを同じ値にし、同時送信要求（調停）が発生する構成に
  しておく。

## 手順

1. **US-1: 構成読み込みと基本実行**
   - アプリを起動し、上記の設定ファイルを読み込ませる。
   - シミュレーション時間 10秒を指定して実行する。
   - **期待結果**: エラーなく実行が完了し、CSV ログ（`contracts/log-output-format.md` の列
     定義）が出力される。各フレームの送信行数が、概ね `10秒 ÷ 周期` に一致する。

2. **US-1: 構成エラーの拒否**
   - ノードを17個に増やした構成、または同じ ID を2ノードに設定した構成を読み込ませる。
   - **期待結果**: シミュレーションは開始されず、エラーメッセージ（ノード数超過 or ID重複）が
     表示される。

3. **US-2: 調停と自動再送信**
   - 手順1のログを開き、`CAN_ID=0x080` と `CAN_ID=0x100` の最初の送信について、
     `Tx_Start` を比較する。
   - **期待結果**: `0x080` の `Tx_Start` が `0x100` より早い。`0x100` の該当行は
     `Status=ARBITRATION_LOST_RETRY` かつ `Retry_Count>=1` になっている。
     実測値（機能 002 のスタートアップ制御を実装した後、`sample_appendix_a.cfg` を使用）:
     `0x080` の初回 `Tx_Start` = 162 µs、`0x100` の初回 `Tx_Start` = 598 µs。機能 002 の実装前は
     それぞれ 140 µs / 576 µs で、差の 22 µs は各ノードが通常動作に入るまでのバス同期時間
     （11ビット時間）。大小関係と `Status` / `Retry_Count` は機能 002 の前後で変わらない。

4. **US-3: 性能指標の評価**
   - シミュレーション終了時に出力される集計結果（`contracts/log-output-format.md` の
     「集計サマリ出力」）を確認する。
   - **期待結果**: ID ごと・ノードごと・全体で、総送信レイテンシ／送信待ち遅延／フレーム伝送
     時間／バス負荷率／ジッターの値が表示される。`Bus_Load_Pct` はドメイン仕様書 付録Aの
     試算値（約7.8%、500 kbps時）**を上回らない**（付録Aの値は最悪ケースのスタッフビット数を
     前提とした見積りであり、実際のデータ列から算出される値はこれより小さくなる）。

5. **再現性（SC-001）**
   - 手順1と同じ構成・同じシミュレーション時間で再実行する。
   - **期待結果**: 出力される CSV ログが1バイト単位で完全に一致する。
