# Feature Specification: CAN バスシミュレーション コア機能（構成・調停・性能評価）

**Feature Branch**: `001-can-simulation-core`

**Created**: 2026-09-28

**Status**: Draft

**Input**: User description: "US-1〜US-3をまとめた初期版一式：ネットワーク構成とシミュレーション実行、調停と自動再送信の確認、性能指標の評価。出典: Doc/CANバスシミュレータ仕様.md（Draft v1.0）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ネットワークを構成してシミュレーションを実行する (Priority: P1)

利用者は、ノード（最大16）と各ノードの送信フレーム一覧（ID・DLC・データ・送信周期）を設定
情報として与え、指定した時間だけシミュレーションを実行できる。実行後には、各フレームが周期
どおりに送信された記録（ログ）が得られる。

**Why this priority**: これがなければシミュレータとして成立しない。他の全ユーザーストーリー
（調停確認、性能評価）はこの基本実行機能の上に成り立つため、最初に提供すべき MVP である。

**Independent Test**: サンプル構成（6ノード・500 kbps、付録A相当のフレーム一覧）を読み込ませ、
10秒間実行する。全フレームが周期どおりに送信されたことを示すログが出力されれば、このストー
リー単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 6ノード・500 kbps の構成（各ノードに1つ以上の送信フレームを設定）、**When** 10秒間
   シミュレーションを実行する、**Then** 各フレームが設定した周期どおりに送信され、送信・受信の
   記録がログに残る。
2. **Given** 17ノードを含む構成、または同じ ID を2つのノードが送信する構成、**When** その構成を
   読み込む、**Then** 構成エラーとして拒否され、拒否理由（ノード数超過／ID重複）が利用者に示さ
   れる。

---

### User Story 2 - 調停と自動再送信を確認する (Priority: P2)

利用者は、複数のノードが同時に送信を要求した場合に、CAN の優先度規則（ID が小さいほど優先）
に従って調停が行われ、負けたノードのフレームが自動的に再送信されることを確認できる。

**Why this priority**: 複数ノードが同時に送信要求を出す状況は CAN バスの基本動作であり、
User Story 1 の「基本実行」の上に成り立つ振る舞いの正しさを保証する。性能評価（User Story 3）
の指標（送信待ち遅延など）はこの調停結果に依存するため、性能評価より先に確立する必要がある。

**Independent Test**: 同一時刻に異なる ID（優先度の異なる）2フレームの送信要求が同時に発生する
構成を用意し、実行する。ID の小さいフレームが先に送信され、負けたフレームの再送信とログ上の
再送信回数が確認できれば、このストーリー単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** ID 0x080 と 0x100 が同一時刻に送信要求を出す構成、**When** シミュレーションを実行
   する、**Then** 0x080（ID が小さい方）が先に送信され、0x100 は 0x080 の送信完了後（送信終了と
   フレーム間休止期間のあと）に送信される。0x100 のログには調停負けと再送信回数1が記録される。

---

### User Story 3 - 性能指標を評価する (Priority: P3)

利用者は、シミュレーション実行後にログを集計し、総送信レイテンシ・送信待ち遅延・フレーム伝送
時間・バス負荷率・ジッターといった性能指標を得ることができる。

**Why this priority**: 性能評価はシミュレータの最終的な提供価値（バスの性能を見積もる）である
が、正しい送受信記録（User Story 1）と正しい調停結果（User Story 2）が土台として必要なため、
優先度は3番目とする。

**Independent Test**: User Story 1・2 の実行結果（ログ）に対して集計処理を行い、4つの指標
（総送信レイテンシ、送信待ち遅延、フレーム伝送時間、バス負荷率）とジッターが算出できれば、
このストーリー単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** シミュレーション実行済みのログ、**When** 集計処理を実行する、**Then** ID ごと・
   ノードごと・全体で、総送信レイテンシ／送信待ち遅延／フレーム伝送時間／バス負荷率／ジッター
   （最大・最小・標準偏差）が算出される。

---

### Edge Cases

- 送信要求の時点でバスが他ノードの送信中である場合、要求元ノードは「自動再送信準備」状態で
  待機し、バスがアイドルになった時点で調停に参加する。
- 送信待ちの間に同じフレームの次の周期の送信要求が来た場合、データは最新値で上書きされ、
  最初の送信要求時刻は保持されたまま上書き回数が記録される。
- 同じ時刻に複数の種類のイベント（送信完了、送信要求、バスアイドルなど）が発生した場合、
  定められた優先順序とノード番号順で決定的に処理され、同一構成からは常に同一の結果が得られる。
- バス負荷率が100%に近く、優先度の低いフレームがいつまでも送信できない状態（送信飢餓）に
  陥っても、シミュレーションはエラー停止せず、再送信回数の増加としてログに記録され続ける。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、1本のバスに接続する 1〜16 ノードの構成を受け付けなければならない。
  17ノード以上の構成は読み込み時に拒否しなければならない。
- **FR-002**: システムは、バスの通信速度を 125k / 250k / 500k / 1Mbps から選択できなければ
  ならない（既定値: 500 kbps）。
- **FR-003**: システムは、各ノードに対して送信フレーム一覧（ID・DLC・データ・送信周期・初回
  オフセット）を設定として受け付けなければならない。データのバイト数が DLC と一致しない構成
  は読み込み時に拒否しなければならない。
- **FR-004**: システムは、同一 ID を複数のノードが送信する構成を読み込み時に拒否しなければ
  ならない（1つの ID を送信するノードは1つに限る）。
- **FR-005**: システムは、各ノードに受信フィルタ（受信する ID の集合）を設定できなければなら
  ない。未指定の場合は全 ID を受信対象とする。
- **FR-006**: システムは、イベント駆動方式（時刻順に並んだイベントを1つずつ処理する方式）で
  シミュレーションを進行させなければならない。イベントはビット単位ではなくフレーム単位で
  発生させる。
- **FR-007**: システムは、同一時刻に複数のイベントが発生した場合、定められた種類ごとの優先順序
  とノード番号の昇順で処理しなければならない。これにより、同一構成からは常に同一の実行結果が
  得られなければならない（再現性）。
- **FR-008**: システムは、CAN 2.0A 標準フォーマット（SOF/ID(11bit)/RTR/IDE/r0/DLC/データ0〜8
  バイト/CRC/CRCデリミタ/ACKスロット/ACKデリミタ/EOF）でフレームを表現しなければならない。
- **FR-009**: システムは、ビットスタッフィング（同一レベル5ビット連続で反転ビットを1つ挿入）を
  適用したビット数からフレームの伝送時間を計算しなければならない。
- **FR-010**: システムは、フレーム送信後に3ビットのフレーム間休止期間（インターミッション）を
  設け、その間は新しい送信を開始してはならない。
- **FR-011**: システムは、送信待ちの間に同じフレームの次の周期の送信要求が発生した場合、
  送信データを最新値で上書きし、上書き回数を記録しなければならない。最初の送信要求時刻は
  変更してはならない。
- **FR-012**: システムは、複数のノードが同時に送信を要求した場合、送信フレームの ID が最も小
  さいノードを調停の勝者としなければならない。
- **FR-013**: システムは、調停に負けたノードについて、そのフレームの再送信回数を1増やし、
  勝者フレームの送信完了後に自動的に再送信を試みなければならない。
- **FR-014**: システムは、1つのノードが複数の送信待ちフレームを持つ場合、ID の小さい順に調停
  へ提出しなければならない。
- **FR-015**: システムは、送信が成功したフレームについて、通常動作中かつ受信フィルタに合致する
  送信元以外の全ノードに受信させなければならない。
- **FR-016**: システムは、受信完了時刻に、各受信ノードに設定された受信処理遅延（既定 0 µs）を
  加えた時刻を受信処理時刻として記録しなければならない。
- **FR-017**: システムは、1フレーム×受信ノードごとに1行のログを出力しなければならない
  （受信ノードがないフレームは送信側の情報のみで1行出力する）。ログには少なくとも、時刻、
  CAN ID、DLC、送信ノード／受信ノード、送信要求／開始／完了時刻、受信開始／完了／処理時刻、
  バス負荷率、ステータス（成功／調停負けで再送信）、再送信回数、上書き回数を含めなければ
  ならない。
- **FR-018**: システムは、ログから次の指標を算出できなければならない: 総送信レイテンシ
  （受信処理時刻 − 送信要求時刻）、送信待ち・調停遅延（送信開始時刻 − 送信要求時刻）、
  フレーム伝送時間（送信完了時刻 − 送信開始時刻）、バス負荷率（一定時間窓内の送信時間の
  合計に対する割合）。
- **FR-019**: システムは、ID ごとに、連続する送信開始時刻の間隔と設定周期との差からジッター
  （最大・最小・標準偏差）を算出できなければならない。
- **FR-020**: システムは、算出した性能指標を ID ごと・ノードごと・全体で集計して提示できなけ
  ればならない。
- **FR-021**: システムは、利用者が指定したシミュレーション時間でシミュレーションを終了しなけ
  ればならない。

### Key Entities *(include if feature involves data)*

- **ネットワーク**: バスの通信速度と、接続されたノードの一覧（1〜16台）を表す。バスは1本。
- **ノード**: 番号・名称・送信フレーム一覧・受信フィルタ・受信処理遅延を持つ。送信状態
  （アイドル／調停中／送信完了／調停負け待機／再送信準備）を1つ持つ。
- **送信フレーム定義**: ID・DLC・データ・送信周期・初回オフセットを持ち、1つのノードに属する。
- **送信待ちフレーム**: 送信フレーム定義・送信要求時刻・現在のデータ・再送信回数・上書き回数を
  持ち、ノードの送信待ち行列に並ぶ。
- **ログ行**: 1フレーム×受信ノードごとの送受信記録一式（時刻群・ID・ステータス・再送信回数・
  上書き回数・バス負荷率など）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同一構成で2回シミュレーションを実行したとき、出力されるログが完全に一致する
  （再現性100%）。
- **SC-002**: 複数ノードが同時に送信要求を出すあらゆるケースで、ID が最も小さいフレームが
  例外なく先に送信される。
- **SC-003**: 算出されたフレーム伝送時間が、ビット列（スタッフビット込み）から手計算した値と
  完全に一致する。
- **SC-004**: バス負荷率が100%未満の構成で一定時間実行したとき、各フレームの送信回数が
  「(実行時間 − 送信開始可能になった時刻 − 初回オフセット) ÷ 送信周期」の切り上げ値と一致する。
- **SC-005**: 16ノードの構成は正常に読み込まれて実行でき、17ノード以上の構成は必ず拒否される。
- **SC-006**: 性能指標（総送信レイテンシ・送信待ち遅延・フレーム伝送時間・バス負荷率・
  ジッター）を、実行後にログから手作業で追加計算することなく確認できる。

## Assumptions

- 本機能は、各ノードが起動シーケンス（電源投入・初期化・バス同期検出）を完了し、通常動作
  モードに入っていることを前提とする。起動シーケンス自体の詳細な検証（電源投入時刻のばらつき
  など）は別機能（User Story 4 相当）として今後 `/speckit.specify` で扱う。
- エラー状態制御（エラーパッシブ・バスオフ等）は本機能のスコープ外とする。送信は常に ACK が
  返り成功するものとし、エラーによる再送信は発生しない（Doc/CANバスシミュレータ仕様.md の
  スコープ境界に準拠）。
- 対象は CAN 2.0A 標準フォーマット（11ビットID）のデータフレームのみとする。拡張フォーマット
  （29ビットID）・CAN FD・リモートフレーム・オーバーロードフレームは対象外とする。
- 電気的な物理層（差動電圧・終端抵抗・伝搬遅延・ビットタイミング・クロック誤差）は模擬せず、
  全ノードが理想的に同期しているものとみなす。
- 既定の動作確認用構成として、Doc/CANバスシミュレータ仕様.md 付録A（6ノード・8フレームの
  サンプル）を使用できるものとする。
- ネットワーク・ノードの設定入力形式（設定ファイルのフォーマット）は、本機能の実行方法
  （手動入力／設定ファイル読み込みなど）を決める `/speckit.plan` 以降で確定する。本仕様は
  「設定として何を与えられるか（内容）」のみを規定し、「どのような形式で与えるか」は規定
  しない。
- ログの出力形式（CSV／JSON Lines 等）や保存先は、実装方式を決める `/speckit.plan` 以降で
  確定する。本仕様は「ログにどの情報が含まれるべきか（内容）」のみを規定する。
- バス負荷率の集計時間窓は既定 100 ms とする（Doc/CANバスシミュレータ仕様.md の既定値を踏襲）。
