# Feature Specification: 解析メニューの送信待ち時間と送信ジッター

**Feature Branch**: `ver.0.7`（spec ディレクトリ: `029-tx-wait-jitter-analysis`）

**Created**: 2026-10-05

**Status**: Draft

**Input**: User description: "次の①、②の解析項目を解析メニューに追加してください。①送信待ち時間(W): CAN ID ごとの Tx_Start − Tx_Request の表とヒストグラム ②送信ジッター(J): CAN ID ごとの、周期からのずれの表とグラフ"（確認の回答: Q1 = A（時刻に沿ったずれの推移）、Q2 = A（送信待ち時間・受信完了時間・送信ジッター・区切り線・CAN バス負荷の順））

**前提となる機能**: 機能 001（ログの CSV 形式、FR-019 のジッターの定義）、008（送信バッファの満杯による破棄）、025（解析・ログ表示メニュー）、027（ログクリア）、028（受信完了時間・CAN バス負荷のウィンドウ）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - CAN ID ごとの送信待ち時間を見る (Priority: P1)

ユーザーはシミュレーションを実行した後、「解析 → 送信待ち時間」で、各フレームが送信を要求されてから実際にバスへ送り出し始めるまでの時間（送信待ち時間）を CAN ID ごとに確かめる。
表で CAN ID ごとの件数・最小・平均・最大などを比べ、ヒストグラムで待ち時間のばらつきを見る。優先度の低い（CAN ID の大きい）フレームほど待たされる様子や、
どの CAN ID が調停負け・バスの使用中で遅れているかを、CSV を加工しなくてもわかるようにする。

**Why this priority**: 要望の 1 つ目。028 の受信完了時間は「待ち」と「伝送」を合わせた時間なので、遅れの原因が待ちにあるかを見分けるにはこの指標が要る。

**Independent Test**: 16 ECU の車両サンプルを実行し、「送信待ち時間」を開いて、全体の件数がログの送信の回数と一致すること、選んだ行のヒストグラムの度数の合計がその行の件数と一致することを確かめる。

**Acceptance Scenarios**:

1. **Given** 現在のプロジェクトのフレームログがある、**When** 「解析 → 送信待ち時間」を選ぶ、**Then** ウィンドウが開き、表とヒストグラムが表示される。
2. **Given** ウィンドウ、**When** 表を見る、**Then** 先頭に全体の行、続いて CAN ID ごとの行が CAN ID の小さい順（優先度の高い順）に並び、
   各行に CAN ID・送信 ECU・件数・最小・平均・最大・95 パーセンタイル（µs）が表示される。行が多いときは表をスクロールして見る。
3. **Given** 表、**When** 行を選ぶ、**Then** ヒストグラムがその行の待ち時間の分布に切り替わる。全体の行を選ぶと全体の分布になる。
4. **Given** 待ち時間の定義、**When** 集計する、**Then** 送信 1 回ごとに、送信要求の時刻から送信開始の時刻までを 1 件の時間とする。
   受信 ECU の数だけログの行があっても、同じ送信は 1 件と数える。調停負けで再送されたフレームは、最終的に送れた 1 回を 1 件とする（時間は再送までの待ちを含む）。
5. **Given** ヒストグラム、**When** 見る、**Then** 横軸は時間（µs）、縦軸は件数で、ビンの幅・範囲は分布に合わせて自動で決まり（028 の受信完了時間と同じ規則）、軸に目盛りと値が表示される。

### User Story 2 - CAN ID ごとの送信ジッターを見る (Priority: P1)

ユーザーは「解析 → 送信ジッター」で、周期送信のフレームが本来の周期からどれだけずれて送られたか（送信ジッター）を CAN ID ごとに確かめる。
表で CAN ID ごとのずれの最小・最大・ばらつきを比べ、グラフで選んだ CAN ID のずれの様子を見る。

**Why this priority**: 要望の 2 つ目。周期の安定性は、受信側の制御（タイムアウト判定など）に直結する評価指標である。

**Independent Test**: 16 ECU の車両サンプルを実行し、「送信ジッター」を開いて、表の値が集計 CSV（`.summary.csv`）の CAN ID ごとのジッターの最大・最小・標準偏差と一致すること
（破棄の無い構成）、グラフの点の数がその CAN ID の件数と一致することを確かめる。

**Acceptance Scenarios**:

1. **Given** 現在のプロジェクトのフレームログがある、**When** 「解析 → 送信ジッター」を選ぶ、**Then** ウィンドウが開き、表とグラフが表示される。
2. **Given** ウィンドウ、**When** 表を見る、**Then** CAN ID ごとの行が CAN ID の小さい順に並び、各行に CAN ID・送信 ECU・周期（ms）・件数・最小・最大・標準偏差（µs）が表示される。
3. **Given** ジッターの定義、**When** 集計する、**Then** 同じ CAN ID の連続する 2 回の送信について、「送信開始の間隔 − 本来の周期」を 1 件のずれとする（機能 001 の FR-019 と同じ定義）。
   正は遅れ、負は早まりを表す。
4. **Given** 表、**When** 行を選ぶ、**Then** グラフがその CAN ID のずれに切り替わる。グラフは時刻に沿ったずれの推移で、横軸を時刻（ms）、縦軸をずれ（µs）とし、各送信のずれを点で描いて折れ線でつなぐ。ずれ 0 の線を描き、軸に目盛りと値を付ける（確認の回答 Q1 = A）。点が画面の幅より多いときは、028 のバス負荷のグラフと同じく 1 列ごとに間引くが、その列の最大と最小の両方を残して山と谷を見落とさない。
5. **Given** 送信が 1 回しか無い CAN ID、**When** 表を見る、**Then** 件数 0 として行を表示し、最小・最大・標準偏差は空欄にする（ずれを計算できない）。

### User Story 3 - メニューの並びと、解析できないときの通知 (Priority: P2)

「解析」メニューに 2 つの項目が加わる。プロジェクトファイルが無い・ログが無い・読めないときは、理由を通知する（028 と同じ）。

**Why this priority**: 項目の置き場所と、何も表示されない理由がわかることは、使い始めの迷いを減らす。

**Independent Test**: 起動直後のメニューの並びと Alt+W・Alt+J を確かめる。起動直後・ログの無いプロジェクト・ログクリアの後に 2 つの項目を選び、通知を確かめる。

**Acceptance Scenarios**:

1. **Given** 起動直後、**When** 「解析」を開く、**Then** 「送信待ち時間(W)」「受信完了時間(R)」「送信ジッター(J)」、区切り線、「CAN バス負荷(B)」の順に項目がある（確認の回答 Q2 = A。送信から受信の流れの順）。
2. **Given** 「解析」を開いている、**When** W・J を押す、**Then** それぞれ「送信待ち時間」「送信ジッター」が選ばれる。
3. **Given** プロジェクトファイルが無い・ログが無い・ログが読めない、**When** どちらかの項目を選ぶ、**Then** 028 と同じ通知が出て、ウィンドウは開かない。

### Edge Cases

- 実行中・中断中は「解析」メニューはグレーで開けない（機能 025 のまま）。
- 破棄された送信（OVERWRITE。送信していない）は、送信待ち時間にもジッターにも含めない。送信待ち時間のウィンドウに破棄の件数を表示する。
- 破棄で 1 回分の送信が抜けた場合、ジッターは「送信開始の間隔 − 送信要求の間隔」で計算し、抜けた周期をずれとして数えない（本来の周期の倍数の間隔になっても、ずれは待ち時間の差だけになる）。
  そのため、破棄のある構成では、集計 CSV（周期をそのまま引く）とは値が違ってよい。
- 送信の行が 1 件も無いログ: どちらの表も全体（送信待ち時間）または 0 行（ジッター）で、グラフは空の表示にする。
- 大きなログ（600 秒・数百万行）でも、028 と同じく数秒以内に開く。
- ウィンドウを開いたまま、新しい実行の「開始」・読込み・セッティング・ログクリアを行うと、そのウィンドウは閉じる（028 の解析のウィンドウと同じ）。
- 同じ項目をもう一度選んだときは、開いているウィンドウを前面に出すだけ。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 「解析」メニューに「送信待ち時間(W)...」と「送信ジッター(J)...」の 2 項目を加え、項目を「送信待ち時間・受信完了時間・送信ジッター・区切り線・CAN バス負荷」の順に並べなければならない。アクセスキーは W・J（既存の R・B はそのまま）とする。
- **FR-002**: どちらも、現在のプロジェクトのフレームログ（`.log.csv`）を元に計算しなければならない。
- **FR-003**: 「送信待ち時間」は、送信 1 回ごとの「送信開始 − 送信要求」を、全体と CAN ID ごとに、件数・最小・平均・最大・95 パーセンタイルの表にしなければならない。CAN ID の行には送信 ECU も表示する。
- **FR-004**: 「送信待ち時間」は、表で選んだ行の分布のヒストグラムを、軸の目盛りと値付きで表示しなければならない（ビンの規則は 028 と同じ）。
- **FR-005**: 「送信ジッター」は、CAN ID ごとに「連続する送信開始の間隔 − 本来の間隔」を求め、周期・件数・最小・最大・標準偏差を表にしなければならない。
  本来の間隔は、その 2 回の送信要求の間隔とする（周期どおりなら周期そのもの）。
- **FR-006**: 「送信ジッター」は、表で選んだ CAN ID のずれのグラフを、軸の目盛りと値付きで表示しなければならない（時刻に沿ったずれの推移。US2-4）。
- **FR-007**: プロジェクトファイルが無い・ログが無い・読めない、のときは、028 と同じ通知を出し、ウィンドウを開いてはならない。
- **FR-008**: 実行中・中断中は選べてはならない。開いているウィンドウは、028 の解析のウィンドウと同じ契機（新しい実行の「開始」・読込み・セッティング・プロジェクトファイルの変更・ログクリア・メインウィンドウを閉じる）で閉じなければならない。
- **FR-009**: 表示は読み取り専用で、ログファイル・プロジェクトを変更してはならない。
- **FR-010**: 既存の「受信完了時間」「CAN バス負荷」とシミュレーションの計算・CSV の出力の内容を変えてはならない。

### Key Entities

- **送信の記録**: フレームログの行を、送信 1 回（送信 ECU・CAN ID・送信開始の時刻が同じ行）にまとめたもの。CAN ID・送信 ECU・送信要求／開始の時刻を持つ。
- **送信待ち時間の集計行**: 全体または CAN ID ごとの、件数・最小・平均・最大・95 パーセンタイルと、時間の一覧（ヒストグラムの元）。
- **ジッターの集計行**: CAN ID ごとの、周期・件数・最小・最大・標準偏差と、ずれの一覧（時刻付き。グラフの元）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 送信待ち時間の全体の件数が、フレームログの送信の回数（受信 ECU の数だけの重複を除き、破棄を除いた数）と一致する（100%）。
- **SC-002**: 送信待ち時間のどの行でも、ヒストグラムの度数の合計がその行の件数と一致する。CAN ID ごとの件数の合計が全体の件数と一致する。
- **SC-003**: 破棄の無い構成で、ジッターの最小・最大・標準偏差が、集計 CSV の CAN ID ごとの値と一致する（四捨五入の差を除く）。手で計算できる小さな構成で、ずれが手計算と一致する。
- **SC-004**: 16 ECU の車両サンプル（5 秒、約 4,000 フレーム）で、どちらのウィンドウも、メニューを選んでから 1 秒以内に表示される。
- **SC-005**: 既存の検証（機能 001〜028 の自動検証）がすべて通り、シミュレーション結果（CSV）は変わらない。

## Assumptions

- 元にするのは、028 と同じく現在のプロジェクトのフレームログ（ファイル）とする。周期もプロジェクトの設定ではなくログから求める（連続する送信要求の間隔。送信要求は周期どおりに出るので、周期そのものになる）。
  そのため、実行後にプロジェクトの周期を変えても、解析の結果は実行したときの値になる。
- 表の「周期」は、その CAN ID の送信要求の間隔のうち最も多い値とする（周期どおりなら 1 つの値）。
- 送信待ち時間の 95 パーセンタイル・ヒストグラムのビンの決め方は、028 の受信完了時間と同じ（最近順位法、10〜50 本のきりの良い幅）。
- 標準偏差は母標準偏差（件数で割る）とし、集計 CSV と同じ計算にする。
- 表示はモードレスのウィンドウで、028 の 2 つのウィンドウと同じ作り（✖・Esc で閉じる、大きさを変えられる）とする。CAN ID は「0x0A0」の形、送信 ECU は「ECU 03」の形で表示する。
- 表やグラフを画像・CSV に書き出す機能は今回の範囲に含めない。
- メニューの項目名・表の見出しなど日本語の文字列は `.rc` に置く。

## 改訂 1（2026-10-05、手動確認を受けて）

ユーザーの手動確認で、600 秒のログ（約 193 万行）では解析に 2 分近くかかり（手順 5）、その間メニューの「解析」もグレーにならない（手順 7）ことがわかった。
ユーザーの提案（解析中のウィンドウと中断ボタン）を受けて、次のとおり改める（この節が上の記述に優先する）。028 の「受信完了時間」「CAN バス負荷」も同じ読み込みを使うので、4 項目すべてに当てはまる。

- **A. 読み込みの速さ**（SC-004 に追加）: 600 秒のログ（16 ECU の車両サンプル、約 193 万行）で、読み込みと計算を合わせて、最適化ありのビルド（Release）で数秒以内、
  最適化なしのビルド（Debug）でも 20 秒以内に終わる。計算の結果は変えない。
- **B. 解析中のウィンドウと中断**（FR-011 を追加）: 「解析」の 4 項目のどれかを選んだとき、ログの読み込みと計算に 0.5 秒より長くかかる場合は、
  「解析中」のウィンドウを出す。
  - ウィンドウには、進み具合（読み込んだ割合のバーと、「ログを読み込んでいます」「集計しています」の表示）と「中断」ボタンがある。
  - ウィンドウが出ている間は、メインウィンドウ（メニュー・ツールバー・構成図）を操作できない。
  - 「中断」（または Esc・✖）を押すと、読み込みをすぐに止め、結果のウィンドウは開かず、メッセージも出さない（集計の途中で押したときは、集計が終わるのを待ってから閉じる）。
  - 0.5 秒以内に終わるときは、ウィンドウを出さずに結果のウィンドウを開く（一瞬だけ出て消えるのを防ぐ）。
  - プロジェクトファイルが無い・ログが無いの通知は、今までどおり解析中のウィンドウより先に出す。読めないときの通知は、解析中のウィンドウを閉じた後に出す。
- 変えないもの: 結果のウィンドウの中身・計算の定義・メニューの並び・閉じる契機。
