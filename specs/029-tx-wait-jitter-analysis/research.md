# Research: 解析メニューの送信待ち時間と送信ジッター

## R1. 送信 1 回のまとめ方

- **Decision**: ログの行のうち Status が `OVERWRITE` 以外で、送信要求・送信開始の時刻がある行を、`(Tx_Node, CAN_ID, Tx_Start)` で 1 つにまとめる。`OVERWRITE` の行は件数だけ数える。
- **Rationale**: ログは「1 フレーム × 受信 ECU」で 1 行なので、受信 ECU の数だけ同じ送信が並ぶ（028 R2）。028 のバス負荷と同じまとめ方にすると、送信の回数が 2 つの解析でそろう。受信 ECU の無い送信も `Rx_Node` が空の 1 行として出るので、ここに含まれる。
- **Alternatives considered**: 行をそのまま数える: 受信 ECU の多いフレームほど件数が膨らみ、待ち時間の分布が偏る。

## R2. 送信待ち時間の統計とヒストグラム

- **Decision**: 028 の受信完了時間と同じ統計（件数・最小・平均・最大・最近順位法の P95）と、同じ `MakeHistogram` を使う。統計の計算は 028 の内部関数（`FillStats`）を、値の配列から統計を作る共通の関数にして両方で使う。
- **Rationale**: 2 つのウィンドウで同じ規則にすると、比べて読める（spec Assumptions）。計算を 1 か所にすると、規則がずれない。

## R3. ジッターの定義と周期

- **Decision**: CAN ID ごとに送信開始の順に並べ、`(Start[k] − Start[k−1]) − (Request[k] − Request[k−1])` をずれとする。周期は送信要求の間隔の最頻値（同数なら小さい方）。
- **Rationale**:
  - 送信要求は通常動作の開始 + 初回オフセット + 周期 × k の時刻に必ず出る（機能 006）ので、連続する送信要求の間隔は周期そのもの。破棄が無ければ機能 001 の FR-019 と同じ値になり、集計 CSV と照合できる（SC-003）。
  - 破棄（送信バッファの満杯）で送信が抜けても、送信要求の間隔は周期の倍数になるので、ずれは待ち時間の差だけになる。FR-019 のように周期をそのまま引くと、抜けた 1 周期がずれとして現れ、グラフに大きな山ができてしまう（spec Edge Cases）。
  - プロジェクトの設定の周期を使わないので、実行後に周期を変えても結果は変わらない（spec Assumptions）。
- **Alternatives considered**:
  - プロジェクトの周期を使う: 実行後の編集で値が変わる。ログと合わない。
  - 送信要求からの遅れ（`Start − Request`）をジッターとする: それは送信待ち時間そのもので、①と同じものになる。

## R4. 標準偏差

- **Decision**: 母標準偏差（`n` で割る）。2 回の走査（平均を出してから二乗和）で計算し、桁落ちを避ける。
- **Rationale**: 集計 CSV（`MetricsAggregator`）が母標準偏差なので、値を照合できる。集計 CSV は `Σx²/n − 平均²` の 1 回の走査だが、値が小さい（µs）ので差は丸めの範囲に収まる。checks では小数第 2 位で比べる。

## R5. ずれのグラフ（Q1 = A）

- **Decision**: `CAnalysisGraph` に `SetDeviation(points, xLabel, yLabel)` を足す。
  - 横軸は時刻（ms、0 から最後の点の時刻まで）、縦軸はずれ（µs）。縦軸の範囲は `min(最小, 0)` 〜 `max(最大, 0)` を `NiceTicks` できりの良い値に広げる（すべて 0 なら −1〜1）。
  - ずれ 0 の線を灰色の実線で描く。
  - 点が描画域の幅（ピクセル）以下なら、各点を小さな四角（3 px）で描き、折れ線でつなぐ。
  - 幅より多いときは `MinMaxPerColumn` で列ごとに最小と最大をまとめ、列ごとに最小から最大への縦線を描き、隣の列の中ほどと線でつなぐ。
- **Rationale**: 028 のバス負荷は負荷の山だけが大事なので列の最大を残したが、ジッターは遅れ（正）と早まり（負）の両方が大事なので、両方を残す。
- **Alternatives considered**: 点だけを描く: 点の少ない CAN ID では流れが読みにくい。折れ線だけ: 点の位置（送信の回）がわかりにくい。

## R6. メニューの並べ替え（Q2 = A）

- **Decision**: `.rc` の「解析(&A)」を「送信待ち時間(&W)... / 受信完了時間(&R)... / 送信ジッター(&J)... / SEPARATOR / CAN バス負荷(&B)...」にする。コマンド ID は新しい 2 つを足すだけで、既存の 2 つ（32785 / 32786）は変えない。
- **Rationale**: 項目の順はメニューの定義の順だけで決まり、ハンドラ・`OnInitMenuPopup`（コマンド ID で扱う）・`UpdateTopMenus`（トップレベルの位置で扱う。「解析」は位置 3 のまま）に影響しない。

## R7. ウィンドウの作り

- **Decision**: `CAnalysisDlgBase` を継承した `CTxWaitDlg`・`CJitterDlg` を足す。並びは 028 の `CLatencyDlg` と同じ（上に一覧、中に説明の 1 行、下にグラフ。一覧は上の 40%）。最初の大きさ 900 × 640、最小 520 × 400 px（028 T017 で、説明の行が切れない大きさとして確かめた値）。
- **Rationale**: 作り・閉じ方・位置決めが 028 と同じになり、閉じる契機は `CloseResultWindows` に 2 つを足すだけで済む（spec FR-008）。
