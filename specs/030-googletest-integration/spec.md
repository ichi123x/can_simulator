# Feature Specification: GoogleTest/CTest による自動テストの導入

**Feature Branch**: `030-googletest-integration`

**Created**: 2026-10-07

**Status**: Implemented

**Input**: User description: "MFCApplication1/CanSim/*.cpp を CMake の静的ライブラリ cansim_core にする（ファイルは移動しない、tools/cansim_runner の空 pch.h を使う）。tests/ に GoogleTest を置き、runTests に cansim_core と gtest_main をリンクする。checks.cpp の検証を機能ごとに GoogleTest へ移す。テスト名に機能番号と SC/FR の ID を付ける。MFCApplication1.sln / .vcxproj と 4 構成ビルドは変えない。checks.exe は移し終えるまで残す。"

**前提となる機能・憲章**: 憲章 v2.0.0 原則 III（自動テスト必須・テストファースト・ctest の実行コマンドを CLAUDE.md に記載）。機能 001〜029 の成功基準を検証している `tools/cansim_runner/checks.cpp`（機能 001〜011・014・015・017〜020・022〜029 の `CheckFeatureNNN`）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 1 つのコマンドでコアロジックの自動テストを実行する (Priority: P1)

開発者が、リポジトリのルートで決まった手順（構成 → ビルド → `ctest`）を実行するだけで、`CanSim/` のコアロジックに対する自動テストが走り、成功・失敗が機能ごと・テストごとに分かる。Visual Studio の「x64 Native Tools Command Prompt」を前提にせず、CMake が使える環境であれば動く。

**Why this priority**: 憲章 III の「自動テスト必須」を実際に満たす土台。これが無いと、以降のテスト移行・テストファーストの運用ができない。

**Independent Test**: クリーンな作業ツリーで構成・ビルド・`ctest` を実行し、少なくとも 1 つの `CanSim/` のロジック（例: フレーム伝送時間の計算）を対象にしたテストが実行され、成功することを確認する。意図的にロジックを壊すとそのテストが失敗することも確認する。

**Acceptance Scenarios**:

1. **Given** 依存物がまだ取得されていない新しい clone、**When** 開発者が手順どおりに構成・ビルド・`ctest` を実行する、**Then** テストが全件実行され、終了コード 0 で終わる。
2. **Given** `CanSim/` のロジックにバグを入れた状態、**When** `ctest` を実行する、**Then** 該当テストが失敗として報告され、終了コードが 0 以外になる。
3. **Given** テストが 1 件失敗した状態、**When** 出力を見る、**Then** どのテスト（機能番号・SC/FR の ID 入り）が失敗したか特定できる。

---

### User Story 2 - 既存の検証（checks.cpp）を機能ごとのテストへ移す (Priority: P2)

`checks.cpp` の機能 001〜029 の検証を、機能ごとにまとまったテストへ移す。テスト名には機能番号と SC/FR の ID が入り、仕様書の項目とテストを対応づけられる。移し終えるまでは `checks.exe` も使えて、両者で同じ項目が検証される。

**Why this priority**: 既存の成功基準の検証資産を自動テストの仕組みに乗せることが、本機能の価値の中心。ただし土台（ストーリー 1）が先に要る。

**Independent Test**: 1 つの機能（例: 機能 001）の検証を移し、移した機能について `checks.exe` と `ctest` の双方が成功し、検証項目の数・内容が対応していることを確認する。機能単位で独立に進められる。

**Acceptance Scenarios**:

1. **Given** 機能 N の検証を移したテスト、**When** `ctest` を実行する、**Then** テスト名から機能 N と対応する SC/FR の ID が分かり、すべて成功する。
2. **Given** 移行の途中、**When** `checks.exe` を従来の手順で実行する、**Then** これまでどおり動作し、全項目が成功する。
3. **Given** 全機能の移行が終わった状態、**When** `checks.cpp` の項目と移行後のテストを突き合わせる、**Then** 移されていない項目が無い（または移さなかった項目とその理由が一覧で記録されている）。

---

### User Story 3 - 既存の Visual Studio ビルドに影響を与えない (Priority: P3)

テスト基盤を足しても、MFC アプリのビルド（`MFCApplication1.sln` / `.vcxproj`、Debug/Release × Win32/x64 の 4 構成）は従来どおり通り、結果のアプリの動作も変わらない。`CanSim/` のソースファイルは今の場所にあり、両方のビルドから同じファイルを使う。

**Why this priority**: 憲章 II（4 構成ビルドの維持）を守るための制約。新機能の価値ではなく、壊さないことの確認。

**Independent Test**: 本機能の変更後に 4 構成すべてを MSBuild でビルドして成功し、`.sln` / `.vcxproj` に差分が無いことを確認する。

**Acceptance Scenarios**:

1. **Given** 本機能の変更を入れた状態、**When** 4 構成をビルドする、**Then** すべて成功する。
2. **Given** 本機能の変更、**When** `git diff` で `.sln` / `.vcxproj` を見る、**Then** 差分が無い。
3. **Given** `CanSim/` のソース、**When** テスト側とアプリ側のビルドを見る、**Then** 同じファイルを（複製せず）使っている。

---

### Edge Cases

- ネットワークに接続できない環境で、テストの依存物（GoogleTest）を取得できない場合は、何が足りないかが分かる失敗になる（黙って 0 件のテストで成功しない）。
- `checks.cpp` が検証に使うファイル（サンプル構成 `SampleConfigs/`・基準 CSV・一時出力先）を、テストが作業ディレクトリや呼び出し方に依存せずに見つけられる。テストが作る一時ファイルは作業ツリーを汚さない。
- GUI 固有の成功基準（目視でしか確認できないもの）は、自動テストの対象外であることが明記され、移行の対象から外れる。
- 600 秒・16 ECU のような時間のかかる検証は、通常の `ctest` を現実的な時間で終えられるよう扱いを決める（分けるか、軽い規模にする）。
- 既存のルート直下の `CMakeLists.txt` / `main.cpp` / `tests.cpp`（動作確認用の仮の雛形、未追跡）が、新しい構成と食い違わない。
- 日本語環境のコードページ 932 でも、`CanSim/` が ASCII のみであるという既存の約束により、文字化け警告（C4819）が増えない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `MFCApplication1/CanSim/` 配下のソース（`*.cpp`）は、ファイルを移動・複製せずに、1 つの静的ライブラリ（`cansim_core`）としてビルドできなければならない。
- **FR-002**: `cansim_core` のビルドは、MFC・Visual Studio のプロジェクトに依存せずに、CMake だけで構成・ビルドできなければならない。`CanSim/` のソースが取り込むプリコンパイル済みヘッダー（`pch.h`）には、`tools/cansim_runner/` にある空の `pch.h` を使う。
- **FR-003**: `tests/` ディレクトリに GoogleTest によるテストを置き、テストの実行ファイル `runTests` は `cansim_core` と GoogleTest の `gtest_main` にリンクして作られなければならない。
- **FR-004**: テストは CTest に登録され、構成・ビルドの後の `ctest` で全件が実行できなければならない。実行コマンドは CLAUDE.md に記載する（憲章 III）。
- **FR-005**: GoogleTest は、開発者が事前に手作業で用意しなくても、構成の手順の中で入手できなければならない（取得元とバージョンは固定して再現性を保つ）。
- **FR-006**: `tools/cansim_runner/checks.cpp` の検証項目（機能 001〜011・014・015・017〜020・022〜029）を、機能ごとにまとまった GoogleTest のテストへ移す。機能ごとに 1 つのテストスイートを作る。
- **FR-007**: テスト名には、対応する機能番号と、仕様書の成功基準（SC）または機能要件（FR）の ID を含める。ID を付けられない項目（改訂の検証など）は機能番号と内容が分かる名前にする。
- **FR-008**: 移したテストは、`checks.cpp` と同等の検証内容（同じ入力・同じ期待）でなければならない。移すときに検証を弱めてはならない。
- **FR-009**: `checks.exe`（`checks.cpp`・`runner.cpp`・README の手順）は、全項目の移行が終わるまで残し、従来の手順で動作し続けなければならない。削除は本機能の範囲外（移行完了後の別作業）とする。
- **FR-010**: テストが必要とする外部ファイル（サンプル構成・基準 CSV）は、リポジトリ内の既存の場所から参照し、複製してはならない。パスは呼び出し方に依存しない形で与える。
- **FR-011**: `MFCApplication1.sln` と `MFCApplication1.vcxproj`（関連する `.filters` を含む）は変更しない。Debug/Release × Win32/x64 の 4 構成のビルドは従来どおり成功しなければならない。
- **FR-012**: `CanSim/` のソースファイル自体の挙動は変えない。テスト基盤のために必要な変更は、ビルド・テスト側に閉じる（ソースの変更が必要なときは、その理由を記録する）。
- **FR-013**: ビルドとテストの生成物（ビルドツリー・取得した依存物・テストの一時出力）は、バージョン管理の対象外にできなければならない。
- **FR-014**: 移行の進み具合（機能ごとの、移した項目数と `checks.cpp` の項目数）を記録し、残りが分かる状態に保つ。

### Key Entities

- **cansim_core（静的ライブラリ）**: `CanSim/` のコアロジックを UI 非依存でまとめたもの。アプリ（MSBuild）とテスト（CMake）の双方が、同じソースファイルから作る。
- **runTests（テスト実行ファイル）**: `cansim_core` と GoogleTest を結んだ実行ファイル。機能ごとのテストスイートを持つ。
- **テストスイート／テストケース**: 機能番号ごとのスイートと、SC/FR の ID を名前に持つテストケース。仕様書の項目との対応表の役割も果たす。
- **移行台帳**: `checks.cpp` の項目と移行後のテストの対応・未移行・対象外（GUI 固有など）の記録。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: クリーンな clone から、構成・ビルド・`ctest` の 3 手順（CLAUDE.md に記載）だけで、全テストが実行・成功する（Visual Studio の IDE を開く必要が無い）。
- **SC-002**: 移行の完了時点で、`checks.cpp` の機能 001〜029 の検証項目の 100% が、GoogleTest のテストへ移されている。GUI 固有などで移せない項目は、理由付きで台帳に載る。
- **SC-003**: すべてのテスト名から、機能番号が読み取れる。SC/FR の ID を持つ検証項目に対応するテストの 100% で、その ID が名前に入っている。
- **SC-004**: `CanSim/` のロジックを意図的に壊すと、対応する機能のテストが少なくとも 1 件失敗する（機能 001・006・008・028・029 の代表 5 機能で確認する）。
- **SC-005**: 本機能の変更後も、4 構成（Debug/Release × Win32/x64）のビルドがすべて成功し、`.sln` / `.vcxproj` の差分が 0 行である。
- **SC-006**: 移行の途中でも、`checks.exe` が従来の手順で実行でき、全項目が成功する（終了コード 0）。
- **SC-007**: 通常の `ctest` の実行は、Release ビルドで 1 分以内（時間のかかる検証を除く）に終わる。

## Assumptions

- 開発環境は Windows 11 + Visual Studio 2022 で、CMake（Visual Studio 付属のものでよい）が使える。CMake のバージョンは 3.22 以上を最低とする（`ctest --test-dir`・`gtest_discover_tests(DISCOVERY_MODE PRE_TEST)`・`TEST_FILTER` のため。実装時に 3.14 から引き上げた）。
- C++ の規格は、既存の `checks.exe` のビルド（`/std:c++14`）と同じか、それ以上で `CanSim/` が通ること。ルートの仮の雛形は C++17。どちらを使うかは計画で決める。
- GoogleTest は、既存の雛形（ルートの `CMakeLists.txt`）と同じく、取得時にバージョンを固定して自動で入手する方式を第一候補とする（「`tests/` に置く」とは、テストのソースと関連する構成を `tests/` 配下に置くことを指す）。
- ルート直下の `CMakeLists.txt`・`main.cpp`・`tests.cpp` は、GoogleTest 導入を試した未追跡の雛形である。本機能の構成はこれを置き換える（最終的に `main.cpp` と `tests.cpp` は不要になる）。扱いは計画で決める。
- 機能の検証は、その機能の中で局所変数を共有しているため、機能ごとに 1 つのテスト（`TEST(FeatureNNN, <SC/FR の ID の並び>)`）として本体を変えずに移す。SC/FR ごとに別のテストへ分けるのは、必要になったときの別作業とする。
- `checks.cpp` の項目の中で、GUI のウィンドウ・描画を必要とするもの（目視でしか確認できないもの）は自動テストの対象外とする。`CanSim/` の座標計算など、UI 非依存の部分の検証は移す。
- 時間のかかる検証（大きなログの読み込み・600 秒の実行）は、通常の `ctest` に含めるか別枠にするかを計画で決める。
- 基準 CSV との比較（機能 004 SC-009 など）は、`checks.exe` と同じく、テストの作る出力と既存の基準ファイルを比べる形を保つ。
- 移行は機能ごとに段階的に進めてよい。1 つの機能を移すごとにテストが通れば、そこで区切れる（区切りの単位は計画で決める）。
- 本機能はテスト基盤とテストの追加が範囲で、アプリの利用者から見える動作の変更は無い。ユーザー向けの画面・メニュー・ファイル形式は変えない。
- 憲章 III（テストファースト）に従い、新しいロジックを足すときは実装より先にテストを書く運用を CLAUDE.md に記載する（本機能自体は、既存ロジックへのテスト追加が中心）。
