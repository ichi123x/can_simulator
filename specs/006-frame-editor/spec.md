# Feature Specification: データフレーム編集ウィンドウ

**Feature Branch**: `006-frame-editor`

**Created**: 2026-09-30

**Status**: Draft

**Input**: User description: "Doc\CANバスシミュレータ仕様.md を v1.11 に更新した。3.1a に従ってデータフレーム編集機能を追加してください。"

**Source**: `Doc/CANバスシミュレータ仕様.md` v1.11 の 3.1a（FR-080〜FR-089a、FR-020a、FR-020b）と、その参照先（FR-004、FR-005、FR-091）。本書の要件番号（FR-001 など）は本機能内の番号で、ドメイン仕様書の番号は括弧で示す。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ノードの送信フレーム一覧を見る (Priority: P1)

利用者は、データフレーム編集ウィンドウを開き、ノード（ECU）を選んで、そのノードが送信するフレームの一覧を見ることができる。一覧には、通し番号、フレーム名、ID、DLC、初回オフセット、送信周期が表示される。

**Why this priority**: 追加・編集・削除のすべてが、この一覧とノードの選択を土台にする。今はフレームの内容を確かめるにもテキストエディタで `.canprj` を開くしかなく、一覧表示だけでも価値がある。

**Independent Test**: `sample_appendix_a` を読み込み、編集ウィンドウで ECU1 を選ぶと、ID 0x100 と 0x101 の2 フレームが、周期 10 ms と 100 ms で表示されることを確認すれば、単独で検証できる。

**Acceptance Scenarios**:

1. **Given** プロジェクトを読み込んだ状態、**When** メニューから編集ウィンドウを開く、**Then** ノードを選ぶ欄と、選んだノードの送信フレーム一覧、「追加」「編集」「削除」のボタンが表示される。
2. **Given** 編集ウィンドウ、**When** ノードを選ぶ、**Then** 一覧には左から「通し番号、フレーム名、ID、DLC、初回オフセット、送信周期」が表示される。ID は 16 進（例 0x100）、初回オフセットと送信周期は ms で表示され、通し番号の順に並ぶ。（Doc FR-086a）
3. **Given** フレームを 1 つも持たないノード、**When** 選ぶ、**Then** 一覧は空で、「追加」だけが押せる。
4. **Given** 選べるノード、**When** ノードの選択欄を開く、**Then** 現在の ECU 数（セッティング）の範囲のECU 1〜N だけが並ぶ。

---

### User Story 2 - フレームを追加する (Priority: P1)

利用者は「追加」を押し、フレーム名、ID、DLC、送信周期、初回オフセットを入力して OK を押すと、そのノードの一覧に新しいフレームが登録される。入力に問題があれば、どの項目がなぜ NG かが示され、入力内容を残したまま再入力できる。

**Why this priority**: 送信フレームを画面から作れることが本機能の中心であり、これがなければテキスト編集が必要なままになる。

**Independent Test**: 空のノードに ID 0x200・DLC 4・周期 20 ms のフレームを追加し、一覧に通し番号 1 で表示され、保存・再読込みしても残り、シミュレーションで 20 ms ごとに送信されることを確認すれば、単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 編集ウィンドウでノードを選んだ状態、**When** 「追加」を押す、**Then** フレーム名・ID・DLC・送信周期・初回オフセットの入力欄と、OK・キャンセルを持つ入力画面が開く。初回オフセットの初期値は 0。（Doc FR-087）
2. **Given** 入力画面、**When** 正しい値を入れて OK を押す、**Then** 一覧の末尾に登録され、通し番号が振られる。
3. **Given** 入力画面、**When** 範囲外の ID（0x800 以上）、範囲外の DLC（9 以上）、他のフレーム（どのノードのものも含む）と重複する ID、1 ms 未満の送信周期、送信周期以上の初回オフセット、のいずれかで OK を押す、**Then** NG の項目と理由が示され、入力画面は閉じず、入力内容は残る。（Doc FR-083、FR-005）
4. **Given** 入力画面、**When** キャンセルを押す、**Then** 何も登録されない。
5. **Given** 入力画面で ID と DLC を入れた状態、**When** 画面を見る、**Then** そのフレームのビット長（スタッフビット込み）と伝送時間（現在の通信速度）が表示される。（Doc FR-085）
6. **Given** 一覧がすでに 100 フレームのノード、**When** 画面を見る、**Then** 「追加」は押せない。（Doc FR-089a、FR-091）

---

### User Story 3 - フレームを編集・削除する (Priority: P1)

利用者は、一覧で選んだフレームを「編集」で変更でき、「削除」で確認のうえ取り除ける。削除すると通し番号は振り直される。

**Why this priority**: 追加だけでは誤りを直せない。一覧の保守に必須。

**Independent Test**: `sample_appendix_a` の ECU1 の 0x101 の周期を 50 ms に編集し、0x100 を削除して、一覧と保存後のファイル、シミュレーション結果に反映されることを確認すれば、単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 一覧でフレームを選んだ状態、**When** 「編集」を押す、**Then** そのフレームの内容が入力済みの入力画面が開き、変更できる。OK 時の検査と NG 時の扱いは追加と同じで、ID の重複検査では編集中のフレーム自身を除く。（Doc FR-088）
2. **Given** 一覧でフレームを選んだ状態、**When** 「削除」を押す、**Then** 通し番号・フレーム名・ID を示した確認が出る。了承すると削除され、残りの通し番号が 1 から振り直される。了承しなければ何も変わらない。（Doc FR-089）
3. **Given** 一覧でフレームを選んでいない状態、**When** 画面を見る、**Then** 「編集」「削除」は押せない。（Doc FR-089a）

---

### User Story 4 - 編集結果をプロジェクトに保存し、シミュレーションで使う (Priority: P2)

利用者が編集ウィンドウで行った変更は、現在のプロジェクトに反映され、プロジェクト保存で `.canprj` に書かれ、シミュレーションの開始で使われる。

**Why this priority**: 編集の結果が保存と実行に届かなければ意味がないが、保存・実行の仕組み自体は機能 004 にあり、ここではつなぐだけのため P2。

**Independent Test**: フレームを追加して保存し、アプリを再起動して読み込むと一覧が同じであること、開始すると追加したフレームがログに現れることを確認すれば、単独で検証できる。

**Acceptance Scenarios**:

1. **Given** フレームを追加・編集・削除した状態、**When** プロジェクトを保存して読み込み直す、**Then** 各ノードの一覧（フレーム名・ID・DLC・周期・初回オフセット・並び順）が保存前と一致する。
2. **Given** 編集した状態、**When** シミュレーションを開始する、**Then** 編集後のフレーム定義で送信される。
3. **Given** シミュレーションの実行中、**When** メニューを見る、**Then** 編集ウィンドウは開けない。

---

### Edge Cases

- ECU 数を減らして、フレームを持つ ECU が範囲外になった場合、その ECU のフレームはプロジェクトに残る（機能 004 と同じ）が、編集ウィンドウでは選べない。ECU 数を戻すと再び選べる。
- 他のノードが使っている ID は、範囲外になった ECU のものを含めて重複として拒否する（ファイルの読込み時の検査と同じ条件にそろえる）。
- フレーム名は空欄でもよい（一覧では空欄として表示）。長さの上限は 32 文字とする。
- 周期が ms の整数でないフレーム（テキストで µs 単位の値を書いた既存ファイル）は、一覧では小数第 3 位までの ms で表示し、編集時は ms の整数で入れ直してもらう。
- 編集ウィンドウを閉じても変更は保存されない（プロジェクト保存が必要。未保存での終了の確認は機能 004 と同じく行わない）。
- 16 ECU × 100 フレームの最大構成でも、一覧の表示と操作ができる。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、送信するデータフレームを登録・編集するウィンドウを、メニューから開けなければならない。シミュレーションの実行中は開けない。（Doc FR-080）
- **FR-002**: 編集ウィンドウでは、ノードを 1 つ選び、そのノードの送信フレーム一覧を表示・編集しなければならない。選べるノードは現在の ECU 数の範囲とする。フレームの送信ノードは、どのノードの一覧に登録したかで決まり、送信ノードの入力欄は設けない。（Doc FR-084）
- **FR-003**: 一覧には、左から通し番号、フレーム名、ID、DLC、初回オフセット、送信周期を表示し、ID は 16 進、初回オフセットと送信周期は ms で表示し、通し番号の順に並べなければならない。（Doc FR-086a）
- **FR-004**: 編集ウィンドウには「追加」「編集」「削除」を置き、フレームが選ばれていないときは「編集」「削除」を、一覧が 100 フレームのときは「追加」を押せないようにしなければならない。（Doc FR-086、FR-089a、FR-091）
- **FR-005**: 追加・編集の入力画面では、フレーム名、ID（16 進）、DLC、送信周期（ms）、初回オフセット（ms、既定 0、空欄は 0）を入力でき、OK とキャンセルを持たなければならない。通し番号とデータは入力しない。（Doc FR-081、FR-087）
- **FR-006**: システムは、OK 時に次を検査し、1 つでも満たさなければ、NG の項目と理由を示して入力画面を閉じず、入力内容を残さなければならない: ID が 0x000〜0x7FF、DLC が 0〜8、ID がプロジェクト内の他のどのフレームとも重複しない（編集時は自身を除く）、送信周期が 1 以上の整数、初回オフセットが 0 以上かつ送信周期未満の整数、フレーム名が 32 文字以内。（Doc FR-083、FR-005、FR-088）
- **FR-007**: 検査に通ったとき、追加はノードの一覧の末尾に登録し、編集は選んだフレームを置き換えなければならない。（Doc FR-087、FR-088）
- **FR-008**: 削除は、対象の通し番号・フレーム名・ID を示して確認し、了承されたときだけ削除しなければならない。（Doc FR-089）
- **FR-009**: 通し番号は、一覧の並び順に 1 から振り、追加・削除のたびに振り直さなければならない。（Doc FR-081）
- **FR-010**: 追加・編集で登録するフレームのデータは、DLC 分のバイトをすべて 0xFF とする。（Doc FR-004、FR-081、FR-082）
- **FR-011**: 入力画面には、入力中の ID・DLC とデータ 0xFF から求めたフレームのビット長（スタッフビット込み）と、現在の通信速度での伝送時間を表示しなければならない。入力値が範囲外のときは表示しない。（Doc FR-085）
- **FR-012**: 編集結果は現在のプロジェクトに反映し、プロジェクト保存で保存され、読込みで復元され、シミュレーションの開始で使われなければならない。フレーム名もプロジェクトに保存する。（Doc FR-084）
- **FR-013**: 1 ノードの一覧は最大 100 フレームとし、ファイルから読み込む場合も 100 を超える一覧は理由を示して読み込まない。（Doc FR-091）
- **FR-014**: フレームのデータは、常に「DLC（編集ウィンドウで設定した値）分のバイトをすべて 0xFF」とし、利用者が値を指定する手段を持たない。プロジェクトファイルにデータの値が書かれていても使わず、読込み時は DLC から0xFF のデータを作る。保存時もデータの値は書かない。既存のサンプル（データ 00 のもの）は、読み込むとデータが0xFF になり、スタッフビット数と伝送時間が変わる。（Doc FR-004、FR-081、FR-082。2026-09-30 利用者決定）
- **FR-015**: 各フレームは、送信ノードが通常動作に入った時刻を起点として、最初の 1 回だけ登録した初回オフセットの分だけ待って送信要求を出し、以後はそのフレームの送信周期ごとに送信要求を繰り返さなければならない（送信要求の時刻 = 通常動作開始時刻 + 初回オフセット + n × 送信周期、n = 0, 1, 2, …）。現在の「シミュレーション開始時刻を起点とする」動作はこれに置き換える。（Doc FR-020a。2026-09-30 利用者決定）

### Key Entities *(include if feature involves data)*

- **送信フレーム定義**: 通し番号（自動）、フレーム名、ID、DLC、データ（0xFF 固定）、送信周期（ms）、初回オフセット（ms）。1 つのノードに属する。
- **ノードの送信フレーム一覧**: ノードごとに 1 つ。最大 100 フレーム。並び順が通し番号になる。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 利用者は、テキストエディタを使わずに、空のノードへフレームを 1 つ追加して保存するまでを 1 分以内に行える。
- **SC-002**: 範囲外・重複・周期とオフセットの関係の誤りを含む入力は、全ケースで登録されず、NG の項目と理由が表示される（100%）。
- **SC-003**: 追加・編集・削除を行って保存し、読み込み直したとき、全ノードの一覧（名前・ID・DLC・周期・オフセット・順序）が保存前と完全に一致する。
- **SC-004**: 入力画面に表示されるビット長が、同じ ID・DLC・データ 0xFF について手計算したスタッフビット込みのビット長と一致する。
- **SC-005**: 追加したフレームは、シミュレーションで「送信ノードの通常動作開始時刻 + 初回オフセット + n × 周期」の時刻に送信要求され（ログの Tx_Request で確認）、10 秒の実行で送信回数が期待値と一致する（バス負荷 100% 未満の構成）。
- **SC-007**: 電源投入時刻をずらしたノード（例: 50 ms）の、初回オフセット 0 のフレームの最初の送信要求時刻が、そのノードの通常動作開始時刻と一致する（シミュレーション開始時刻ではない）。
- **SC-006**: 100 フレームのノードでは「追加」が押せず、101 フレームのノードを含むファイルは読み込まれない。

## Assumptions

- 本機能の範囲は Doc v1.11 の 3.1a（編集ウィンドウ）とする。同じ v1.11 で追加された 3.7a（送信バッファ 16 本・受信バッファ 8 本、満杯時の OVERWRITE）と、ログ列名の Update_Count への変更は、シミュレーションの動作とログ形式の変更であり、別の機能として扱う。
- 編集ウィンドウは、メニュー「編集(E)」に「データフレーム編集」として追加する（開き方は plan で確定）。
- 編集の単位はプロジェクト全体の変更で、編集ウィンドウに「適用」「元に戻す」はない。編集ウィンドウで行った変更はその場で現在のプロジェクトに反映される（保存はプロジェクト保存で行う）。
- フレーム名は既存ファイルにはないため、読込み時は空欄とする。
- FR-014 により既存サンプルの結果（伝送時間・バス負荷・送信待ち遅延など）が変わるため、機能 001〜005 の検証（`checks.exe` の期待値、機能 004 SC-009 の基準 CSV との比較）は、データ 0xFF を前提とした値に更新する。データの値を指定したい要望が将来出た場合は、別機能として扱う。
- FR-015 により、送信要求の起点が「シミュレーション開始時刻」から「通常動作開始時刻」に変わる。電源投入時刻・初期化時間が 0 の構成でも起点は約 11 ビット時間（500 kbps で 22 µs）後ろにずれ、電源投入時刻をずらした構成（機能 002 の `sample_startup` など）では送信要求時刻と送信待ち遅延が大きく変わる。機能 002 の「起動前に発生した送信要求は保留し、通常動作後に送信する」（002 FR-010）は、起点が通常動作開始になるため、起動前の送信要求は発生しなくなる。002 の検証（`checks.exe` の該当項目）は新しい動作に合わせて更新する。
- 送信周期と初回オフセットはファイル上では従来どおり µs で持ち、編集ウィンドウでは ms で扱う（ms × 1000）。
- 受信フィルタ・受信処理遅延・電源投入時刻・初期化時間など、ノードのフレーム以外の設定は本機能では編集しない。
- 通信速度は機能 004 のセッティングの値を使う（伝送時間の表示に使用）。
