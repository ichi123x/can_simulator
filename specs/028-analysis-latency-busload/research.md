# Research: 解析メニューの受信完了時間と CAN バス負荷

## R1. データの元と読み方

- **Decision**: フレームログ（`<プロジェクト>.log.csv`）を 1 回だけ先頭から読む。
  - 必要な列（`CAN_ID`・`Tx_Node`・`Rx_Node`・`Tx_Request`・`Tx_Start`・`Tx_End`・`Rx_End`・`Status`）は、1 行目のヘッダーで列名を探して位置を決める。
  - ヘッダーに必要な列が無い、数値にならない、などは「読めない」（`IDS_LOG_READ_ERROR`）とする。
- **Rationale**:
  - spec の前提（ファイルを元にし、再起動後も解析できる。ログクリアと扱いがそろう）。
  - 列名で探すので、008 で列名が変わった `Update_Count` のような変更が、使わない列で起きても影響しない。
- **Alternatives considered**: 直前の実行の `m_runRows`（メモリ）を使う: 再起動・ほかのプロジェクトの読込みの後に解析できず、ログクリアの後に古い結果が見えてしまう。

## R2. ログの行の意味（実際の出力で確認）

- 各行は「最終的に送れた 1 回の送信 × 受信 ECU」。`Status` の値は次の 3 つ。
  - `SUCCESS`: 調停負けなし
  - `ARBITRATION_LOST_RETRY`: 調停負けの後に送れた。`Retry_Count` が 1 以上
  - `OVERWRITE`: バッファが満杯で捨てられた。受信 ECU と送受信の時刻は空欄
- 受信 ECU の無い送信は、`Rx_Node` が空の行が 1 行になる（時刻はある）。
- **Decision**:
  - 受信完了時間: `Rx_Node` があり、Status が `SUCCESS` か `ARBITRATION_LOST_RETRY` の行。
  - バス負荷: Status が `OVERWRITE` 以外の行を `(Tx_Node, CAN_ID, Tx_Start)` でまとめて、1 回の送信とする。
  - `OVERWRITE` の行は件数だけ数える（受信完了時間のウィンドウに表示する）。
- **Rationale**:
  - spec の Edge Cases（再送は最終的に届いた 1 回、破棄は件数だけ、受信 ECU の数だけ重複して数えない）と一致する。
  - 同じノードは同じ時刻に 2 本を送れないので、`(Tx_Node, Tx_Start)` で送信 1 回が決まる。`CAN_ID` を加えるのは念のため。

## R3. 受信完了時間の終点

- **Decision**: `Rx_End`（受信完了）を終点にする。`Rx_Process`（受信処理遅延の後）は使わない。
- **Rationale**: spec の Assumptions。集計 CSV の「総送信レイテンシ」は `Rx_Process − Tx_Request` なので、受信処理遅延が 0 でない構成では値が違う。この違いはウィンドウの説明の文に書いておく。

## R4. ヒストグラムのビン

- **Decision**:
  - ビンの数の目安は `k = clamp(ceil(sqrt(n)), 10, 50)`。
  - 幅は `(max − min) / k` を 1・2・5 × 10^m に切り上げた値（最小 1 µs）。
  - 始まりは `floor(min / 幅) × 幅`。ビンの数は `max` を含むまで（`[始まり + i × 幅, 始まり + (i+1) × 幅)`）。
  - `n = 0` ならビンなし。`max == min` なら、`[min, min + 1)` の 1 本。
- **Rationale**: 平方根の規則は件数に応じた細かさを与え、10〜50 本に抑えると画面幅で見やすい。きりの良い幅にすると、軸の値が読みやすい（spec の Assumptions）。
- **Alternatives considered**:
  - スタージェスの公式: 件数が多いと粗すぎる（2 万件で 15 本）。
  - 固定幅: 構成によって 1 本に潰れる、または数千本になる。

## R5. 軸の目盛り

- **Decision**: `NiceTicks(lo, hi, 目安の本数)` で、1・2・5 × 10^m の刻みの目盛りを作る。ヒストグラムの横軸・縦軸、バス負荷の横軸に使う。
  - バス負荷の縦軸は 0〜100% の固定（20% 刻み）にする。
  - 平均負荷の水平線は破線で描き、値を添える。
- **Rationale**: 目盛りを純粋関数にして checks で検証できるようにし、2 つのグラフで同じ規則を使う。

## R6. 表示（ウィンドウの作り）

- **Decision**:
  - 2 つのウィンドウはどちらもモードレスで、大きさを変えられる。中身は `OnSize` で並べ直す。
  - **受信完了時間**: 上に一覧（`CListCtrl`、レポート表示・1 行選択）を置き、下にヒストグラムを置く。一覧と図の間に説明の 1 行（定義と破棄の件数）を置く。行の選択（`LVN_ITEMCHANGED`）でヒストグラムを描き直す。最初は全体の行を選ぶ。
  - **バス負荷**: 上に要約の 1 行（平均・最大と、その区間の時刻・範囲）、中ほどに折れ線グラフ、下に ECU ごとの一覧（ECU・送信フレーム数・使用率）を置く。
  - グラフは `CAnalysisGraph`（`CWnd` 派生）1 つで、棒（ヒストグラム）と折れ線（負荷）の 2 種類を描く。メモリ DC で描き、ちらつきを防ぐ。
- **Rationale**: 一覧は Windows 標準のコントロールにすると、スクロール・列幅の変更・選択が手間なく得られる。グラフは単純な線と矩形なので、自前で描いても小さい（憲章 IV）。
- **Alternatives considered**: 表も自前で描く: スクロールと選択を作り直すことになり、025 の `CLogTextView` 並みの量になる。

## R7. ウィンドウを閉じる場所

- **Decision**: メインダイアログに `CloseResultWindows()` を作る。中身は `CloseLogViewer()` に加えて、2 つの解析ウィンドウも閉じる。
  - 025 で `CloseLogViewer()` を呼んでいた場所（新しい実行の開始、読込み、セッティング、`SetProjectPath` でパスが変わるとき、メインを閉じるとき）は、すべてこれに置き換える。
  - 027 のログクリアの「はい」の後も、これに置き換える。
- **Rationale**: spec FR-008。表示中の内容とファイルが食い違う契機は、ログのウィンドウと同じ。1 つの関数にまとめると、閉じ忘れが起きない。
