# Feature Specification: 送信・受信フレームバッファ

**Feature Branch**: `008-frame-buffers`

**Created**: 2026-09-30

**Status**: Draft

**Input**: User description: "Doc\CANバスシミュレータ仕様.mdの3.7a フレームバッファを参照して、送信用フレームバッファ、受信用フレームバッファが実装されているかを確認して実装されていなければ、実装してください。"

**Source**: `Doc/CANバスシミュレータ仕様.md` v1.11 の 3.7a（FR-090〜FR-095）と、関連する FR-024・FR-051（ログの Status とUpdate_Count）。本書の要件番号は本機能内の番号で、ドメイン仕様書の番号は括弧で示す。

**現状の確認結果（2026-09-30）**: 送信バッファ 16 本、受信バッファ 8 本、満杯時の破棄と OVERWRITE の記録、ログの列名Update_Count は、いずれも未実装。同じフレームの送信待ち中に次の周期が来たときのデータ更新（Doc FR-092a、FR-024）だけは実装済み（列名は Overwrite_Count）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 送信バッファの満杯を評価する (Priority: P1)

利用者は、1 つの ECU が同時に送信待ちにできるフレームが 16 本までであることを前提に、送信要求が集中したときに捨てられるフレームを、ログと集計で確認できる。

**Why this priority**: 送信バッファの満杯は、ECU の設計（フレーム数、周期、初回オフセット）の妥当性を評価する中心的な指標であり、Doc 3.7a の主目的。

**Independent Test**: 1 つの ECU に、初回オフセット 0・同じ周期のフレームを 20 個登録して実行し、同時に要求がそろう時刻ごとに、ID の大きい 4 フレームが OVERWRITE としてログに出て、その ECU の送信側の破棄回数が集計に出ることを確認すれば、単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 1 つの ECU に 20 個のフレーム（初回オフセット 0、周期はすべて同じ）、**When** 実行する、**Then** 要求がそろう時刻ごとに、ID の小さい 16 フレームが送信待ちになり、ID の大きい 4 フレームの送信要求は捨てられる。（Doc FR-092b、FR-092c）
2. **Given** 捨てられた送信要求、**When** ログを見る、**Then** そのフレームにつき 1 行があり、Status は OVERWRITE、送信要求時刻は捨てられた要求の時刻、受信ノードと送信・受信の各時刻は空欄である。
3. **Given** 同じ構成、**When** 集計を見る、**Then** その ECU の送信バッファ満杯による破棄回数が、ログの送信側 OVERWRITE 行の数と一致する。
4. **Given** 送信待ちが 16 本未満の状態、**When** すでに送信待ちの同じフレームに次の周期の要求が来る、**Then** 新しいバッファは使わず、データを更新して Update_Count を 1 増やす（従来どおり）。（Doc FR-092a、FR-024）
5. **Given** 送信待ちのフレームの送信が成功した、**When** 次の送信要求が来る、**Then** そのバッファは空いており、新しい要求を受け付ける。（Doc FR-092）

---

### User Story 2 - 受信バッファの満杯を評価する (Priority: P1)

利用者は、各 ECU が受信したフレームを 8 本の受信バッファに貯め、受信処理時刻に 1 本ずつ取り出すモデルで、受信処理が追いつかないときに捨てられるフレームを、ログと集計で確認できる。

**Why this priority**: 受信側の処理能力（受信処理遅延）の評価に必要で、送信バッファと対になる Doc 3.7a の要件。

**Independent Test**: 受信処理遅延を大きく（例: 2 ms）設定した ECU に、短い間隔でフレームが届く構成を実行し、9 本目以降がOVERWRITE として記録され、受信処理時刻が空欄になり、その ECU の受信側の破棄回数が集計に出ることを確認すれば、単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 受信フィルタに合うフレームの受信が完了した、**When** その ECU の受信バッファに空きがある、**Then** フレームは受信完了時刻にバッファに入り、受信処理時刻（受信完了 + 受信処理遅延）にアプリが取り出してバッファが空く。（Doc FR-093）
2. **Given** 受信バッファが 8 本とも埋まっている、**When** 新しいフレームの受信が完了する、**Then** 新しいフレームは捨てられ、その受信ノードの行の Status は OVERWRITE、受信処理時刻は空欄になる。（Doc FR-094）
3. **Given** 受信処理遅延が 0 µs（既定）、**When** 実行する、**Then** 受信バッファの満杯は起きない（受信した瞬間に空く）。（Doc FR-095）
4. **Given** 同じ構成、**When** 集計を見る、**Then** その ECU の受信バッファ満杯による破棄回数が、ログの受信側 OVERWRITE 行の数と一致する。

---

### User Story 3 - ログの列名と既存の結果 (Priority: P2)

利用者は、ログの「送信待ち中にデータを更新した回数」の列を Update_Count という名前で見る。バッファが満杯にならない構成では、Status と各時刻は従来と同じである。

**Why this priority**: Doc v1.8 の決定（列名の変更）と、既存サンプルの結果が意図せず変わらないことの確認。

**Independent Test**: 既存のサンプルを実行し、ログの見出しが Update_Count になり、それ以外の列の値が本機能の前と一致することを確認すれば、単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 任意の構成、**When** ログを出力する、**Then** 最後の列の見出しは Update_Count である。（Doc FR-051）
2. **Given** 送信待ちが 16 本を超えず、受信処理遅延が 0 の既存サンプル、**When** 実行する、**Then** ログ・集計・起動記録は、列名と集計の追加項目を除いて本機能の前と一致する。

---

### Edge Cases

- ECU 数 16 × 100 フレームで、全フレームの要求が同時にそろう場合でも、各 ECU で 16 本までが送信待ちになり、残りは捨てられる。
- 捨てられた送信要求は再送されない。次の周期の要求は通常どおり発生する。
- 送信バッファの満杯判定は「送信待ち（調停に勝って送信中のものも含む）」の本数で行う。送信中のフレームは送信完了（EOF）でバッファを空ける。
- 受信バッファの取り出しは FIFO の順。受信処理時刻は各フレームの「受信完了 + 受信処理遅延」で、受信処理遅延が一定なので到着順と取り出し順は一致する。
- 受信処理の取り出しと、新しいフレームの受信完了が同じ時刻に起きた場合は、取り出しを先に行う（空いたバッファに新しいフレームが入る）。
- シミュレーション終了時に受信バッファに残っているフレームは、受信処理時刻がシミュレーション時間を超えていても、従来どおりログに受信処理時刻を記録する（取り出しの時刻として計算上の値を使う）。
- OVERWRITE の行は、性能指標（レイテンシ、送信待ち遅延、ジッターなど）の計算対象に含めない。フレーム表示（機能 005）では、送信側で捨てられた要求は表示しない。受信側で捨てられたフレームは、バス上では送受信されているので、受信 ECU の強調は従来どおり表示する。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 各 ECU は送信バッファを 16 本、受信バッファを 8 本持たなければならない。（Doc FR-090）
- **FR-002**: 送信要求が発生したとき、同じフレームがすでに送信待ちなら、新しいバッファは使わず、データを更新して更新回数を1 増やさなければならない（送信要求時刻は最初の要求のまま）。（Doc FR-092a、FR-024）
- **FR-003**: 同じフレームが送信待ちでない送信要求は、空いている送信バッファに入り送信待ちにならなければならない。送信待ちが複数あるときは ID の小さい順に調停に出す（従来どおり）。送信が成功したら、そのバッファを空けなければならない。（Doc FR-092）
- **FR-004**: 送信バッファが 16 本とも使用中のときに新しい送信要求（FR-002 に当たらないもの）が発生した場合、その要求を捨て、ログに 1 行（Status = OVERWRITE、送信要求時刻 = その要求の時刻、受信ノードと送信・受信の各時刻は空欄）を出し、その ECU の送信側の破棄回数を 1 増やさなければならない。（Doc FR-092b）
- **FR-005**: 受信フィルタに合うフレームは、受信完了時刻に受信バッファ（FIFO）に入り、受信処理時刻に取り出されてバッファが空かなければならない。（Doc FR-093）
- **FR-006**: 受信バッファが 8 本とも使用中のときに新しいフレームの受信が完了した場合、新しいフレームを捨て、その受信ノードの行の Status を OVERWRITE、受信処理時刻を空欄とし、その ECU の受信側の破棄回数を 1 増やさなければならない。（Doc FR-094）
- **FR-007**: 同じ時刻に受信バッファからの取り出しと新しいフレームの受信完了が起きた場合は、取り出しを先に行わなければならない。
- **FR-008**: ログの「送信待ち中にデータを更新した回数」の列名を Update_Count としなければならない。（Doc FR-051）
- **FR-009**: 集計（性能指標の出力）に、ECU ごとの送信側・受信側の破棄回数を出力しなければならない。
- **FR-010**: OVERWRITE の行は、性能指標の計算対象から除かなければならない。
- **FR-011**: 送信バッファ・受信バッファが満杯にならない構成では、Status・各時刻・回数を本機能の前と同じにしなければならない（列名を除く）。

### Key Entities *(include if feature involves data)*

- **送信バッファ**: ECU ごとに 16 本。1 本に送信待ちのフレームを 1 つ持つ。送信完了で空く。
- **受信バッファ**: ECU ごとに 8 本の FIFO。受信完了で入り、受信処理時刻に出る。
- **破棄回数**: ECU ごとの送信側・受信側の、満杯で捨てたフレームの数。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 1 つの ECU に同時に要求がそろう 20 フレームを置いた構成で、要求がそろうたびに捨てられる送信要求がちょうど4 件で、捨てられるのは ID の大きい 4 フレームである。
- **SC-002**: どの時点でも、各 ECU の送信待ちは 16 本以下、受信バッファは 8 本以下である。
- **SC-003**: 集計の ECU ごとの送信側・受信側の破棄回数が、ログの OVERWRITE 行の数と全 ECU で一致する（100%）。
- **SC-004**: 受信処理遅延 0 の構成では、受信側の OVERWRITE が 0 件である。
- **SC-005**: バッファが満杯にならない既存サンプル 5 つで、ログ・集計・起動記録が、列名と破棄回数の追加を除いて本機能の前と一致する。
- **SC-006**: 同じ構成を 2 回実行したとき、OVERWRITE の行を含めてログが完全に一致する（再現性）。

## Assumptions

- ECU ごとの破棄回数は、集計（`.summary.csv`）の ECU ごとの行（既存の Node グループ）に列を足して出力する。
- 送信側で捨てた要求の行の Timestamp_us は、その送信要求の時刻とする。受信側で捨てた行の Timestamp_us は、受信完了時刻とする（受信処理時刻がないため）。空欄の時刻は CSV では空の値として出力する。
- 送信バッファの本数には、調停に勝って送信中のフレームも含める（送信完了まではバッファを占有する）。
- 送信バッファの 16 本、受信バッファの 8 本は固定値とし、ECU ごとの設定や画面からの変更は本機能では扱わない。
- 受信処理時刻は従来どおり「受信完了 + 受信処理遅延」とし、受信処理の混雑による遅れ（取り出し待ち）は扱わない。
- 機能 005 のフレーム表示と機能 004 の結果出力は、ログの行が増えても従来どおり動く（OVERWRITE 行の扱いは Edge Cases のとおり）。
