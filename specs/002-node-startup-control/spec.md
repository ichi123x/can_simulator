# Feature Specification: ノードのスタートアップ制御（電源投入〜通常動作移行）

**Feature Branch**: `002-node-startup-control`

**Created**: 2026-09-28

**Status**: Draft

**Input**: User description: "US-4: スタートアップ制御。各ノードが『電源投入 → 初期化 → 11ビット連続レセシブ検出 → 通常動作』を経て送信を開始する状態遷移を模擬し、通常動作に入った時刻を記録できるようにする。出典: Doc/CANバスシミュレータ仕様.md US-4 / FR-030〜FR-031c / FR-053"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ノードごとの起動シーケンスを模擬して通常動作開始時刻を確認する (Priority: P1)

利用者は、ノードごとに電源投入時刻と初期化にかかる時間を設定してシミュレーションを実行できる。各ノードは「電源オフ／リセット → 初期化 → バス同期検出 → 通常動作」の順に状態を遷移し、実行後には各ノードがいつ通常動作に入ったかを記録として確認できる。

**Why this priority**: 起動シーケンスの模擬そのものが本機能の中核であり、他の2つのストーリー（起動前の送信要求の保留、送信中バスへの後発参加）はこの状態遷移が存在して初めて意味を持つ。

**Independent Test**: 6ノードそれぞれに異なる電源投入時刻を設定した構成を読み込ませて実行し、各ノードの通常動作開始時刻が記録されていること、その値が「電源投入時刻＋初期化時間＋同期成立までの時間」と一致することを確認すれば、このストーリー単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 6ノードに 0ms / 10ms / 20ms / 30ms / 40ms / 50ms の電源投入時刻を設定した構成、**When** シミュレーションを実行する、**Then** 各ノードが電源投入・初期化完了・通常動作開始の3つの時刻とともに記録され、通常動作開始時刻は電源投入時刻の順序どおりに並ぶ。
2. **Given** 電源投入時刻・初期化時間をどちらも設定しない（既定値）構成、**When** 実行する、**Then** 全ノードが同一時刻に通常動作へ入り、その時刻はバスが空の状態で同期が成立するのに要する時間（11ビット時間）と一致する。
3. **Given** シミュレーション時間より後に電源投入されるノードを含む構成、**When** 実行する、**Then** そのノードは通常動作に到達しなかったことがわかる形で記録され、そのノードのフレームは1件も送信されない。

---

### User Story 2 - 起動前の送信要求が通常動作後に送信されることを確認する (Priority: P2)

利用者は、あるノードが通常動作に入る前に発生した送信要求が破棄されず、通常動作に入った後に送信されることを確認できる。

**Why this priority**: 起動シーケンスを導入すると「まだ送信できない期間」が生まれるため、その期間の送信要求の扱いが決まらないと、既存のログ・性能指標（送信待ち遅延）の解釈が破綻する。User Story 1 の状態遷移が前提となるため優先度は2番目。

**Independent Test**: 電源投入時刻を遅らせたノードに、初回オフセット0・短い周期の送信フレームを設定して実行する。通常動作開始より前の送信が1件もなく、通常動作直後に送信が始まり、そのログ行の送信要求時刻が最初の要求時刻のまま保持されていることを確認すれば、単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 電源投入時刻50msのノードに、初回オフセット0・周期10msの送信フレームを設定した構成、**When** 実行する、**Then** そのフレームの最初の送信は通常動作開始後に行われ、それ以前に送信された記録は存在しない。
2. **Given** 同上の構成、**When** 実行後に最初の送信のログ行を確認する、**Then** 送信要求時刻は最初に要求が発生した時刻（オフセット0の時点）のまま記録され、送信待ち遅延として起動待ち時間が含まれる。

---

### User Story 3 - 送信中のバスに後から参加するノードの同期を確認する (Priority: P3)

利用者は、他ノードが送信している最中に同期検出を始めたノードが、そのフレームの終わり（フレーム終端とフレーム間休止期間）で同期を成立させて通常動作に入ることを確認できる。

**Why this priority**: 実際の CAN ネットワークで頻出する「稼働中のバスに後から電源が入る」状況の再現であり、起動時間の見積もり精度に影響する。基本の状態遷移（User Story 1）と保留動作（User Story 2）が確立した後に検証すべき振る舞いのため優先度は3番目。

**Independent Test**: 1つのノードが継続的に送信している構成に、フレーム送信の途中で同期検出を開始するタイミングの電源投入時刻を持つノードを追加して実行する。後発ノードの通常動作開始時刻がその進行中フレームのフレーム間休止期間の終了時刻と一致することを確認すれば、単独で検証できる。

**Acceptance Scenarios**:

1. **Given** ノードAが連続的にフレームを送信している構成に、ノードBの同期検出開始がノードAのフレーム送信中になるよう電源投入時刻を設定、**When** 実行する、**Then** ノードBの通常動作開始時刻は、その進行中フレームのフレーム間休止期間の終了時刻と一致する。
2. **Given** ノードBの同期検出開始が、進行中フレームの残りが同期成立に必要なレセシブ期間に満たないタイミングである構成、**When** 実行する、**Then** ノードBはその機会では同期せず、次に条件を満たす機会（次のフレーム終端、またはバスが十分な時間空いた時点）で通常動作に入る。

---

### Edge Cases

- 全ノードの電源投入時刻・初期化時間が既定値（0）の場合でも、バスが空である期間を一定時間観測してからでないと通常動作に入らないため、すべての送信が一律にその分だけ後ろへずれる。
- 同期検出中に他ノードの送信（ドミナント）が始まった場合、それまでの連続レセシブの計数はやり直しとなる。
- 電源投入時刻がシミュレーション終了時刻より後のノードは、通常動作に到達しないまま終了する。
- 起動待ちの間に同じフレームの送信要求が周期的に繰り返し発生した場合、既存の上書き規則に従ってデータが上書きされ、上書き回数が累積したうえで通常動作後に1回だけ送信される。
- 複数ノードが同一時刻に通常動作へ入り、かつ同時に送信要求を保留していた場合、通常動作移行後最初の調停で優先度（ID）順に送信される。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、各ノードに電源投入時刻と初期化時間を設定として受け付けなければならない。いずれも未指定の場合は 0 とする。
- **FR-002**: システムは、各ノードについて「電源オフ／リセット」「初期化」「バス同期検出」「通常動作」の4つの状態を管理し、この順序でのみ遷移させなければならない。
- **FR-003**: システムは、設定された電源投入時刻に達したノードを「初期化」状態へ遷移させなければならない。
- **FR-004**: システムは、初期化状態に入ってから設定された初期化時間が経過したノードを「バス同期検出」状態へ遷移させなければならない。
- **FR-005**: システムは、バス同期検出状態のノードについて、バス上でフレーム送信が行われていない期間が連続して11ビット時間続いたことを検出した時点で「通常動作」状態へ遷移させなければならない。
- **FR-006**: システムは、他ノードの送信中にバス同期検出を開始したノードについて、その送信の終端側に現れる連続レセシブ期間（フレーム終端＋フレーム間休止期間）が11ビット時間に達する場合、そのフレーム間休止期間の終了時点で通常動作状態へ遷移させなければならない。
- **FR-007**: システムは、同期成立に必要な連続レセシブ期間が途中で途切れた場合（他ノードの送信が始まった場合）、計数をやり直し、次に条件を満たす機会まで同期を成立させてはならない。
- **FR-008**: システムは、通常動作状態でないノードを調停に参加させてはならず、そのノードのフレームを送信してはならない。
- **FR-009**: システムは、通常動作状態でないノードにフレームを受信させてはならない（そのノードを受信側とするログ行を生成してはならない）。
- **FR-010**: システムは、ノードが通常動作状態に入る前に発生した送信要求を保持し、通常動作に入った後に送信しなければならない。保持中の送信要求時刻は最初に要求が発生した時刻のまま変更してはならない。
- **FR-011**: システムは、各ノードの起動状態遷移の記録を、フレームごとのログとは別の記録として出力しなければならない。
- **FR-012**: 起動状態遷移の記録には、少なくともノード番号、ノード名称、電源投入時刻、初期化完了時刻、通常動作開始時刻を含めなければならない。
- **FR-013**: システムは、シミュレーション終了までに通常動作に到達しなかったノードについても、到達しなかったことが判別できる形で記録しなければならない。
- **FR-014**: システムは、起動シーケンスを含めて、同一構成からは常に同一の実行結果（起動記録とフレームログの両方）を生成しなければならない。
- **FR-015**: システムは、性能指標の算出対象を通常動作状態で実際に送信されたフレームに限定しなければならない（送信されなかった保留中のフレームは算出対象に含めない）。

### Key Entities *(include if feature involves data)*

- **ノードの起動設定**: 電源投入時刻と初期化時間。ノードごとに1組持つ。
- **ノードの起動状態**: 電源オフ／リセット・初期化・バス同期検出・通常動作のいずれか1つ。ノードごとに現在値を1つ持つ。
- **起動記録**: ノード1台につき1件。ノード番号・名称・電源投入時刻・初期化完了時刻・通常動作開始時刻（未到達の場合はその旨）を持つ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 電源投入時刻をずらした構成において、各ノードの通常動作開始時刻が「電源投入時刻＋初期化時間＋同期成立までの時間」の手計算値と完全に一致する。
- **SC-002**: 出力されたフレームログのすべての行について、送信開始時刻がその送信ノードの通常動作開始時刻以降である（通常動作前の送信が0件）。
- **SC-003**: バスが常に空の構成では、通常動作開始時刻が「電源投入時刻＋初期化時間＋11ビット時間」と一致する。
- **SC-004**: 他ノードの送信中に同期検出を開始したノードの通常動作開始時刻が、その進行中フレームのフレーム間休止期間の終了時刻と一致する。
- **SC-005**: 同一構成で2回実行したとき、起動記録とフレームログの両方が完全に一致する（再現性100%）。
- **SC-006**: 電源投入時刻・初期化時間をすべて既定値（0）にした構成では、既存機能（`specs/001-can-simulation-core/`）で得られるログに対して、行数・行の順序・CAN ID・送信ノード／受信ノード・ステータス・再送信回数・上書き回数が一切変化しない。時刻列については、送信要求時刻は変化せず、その他の時刻は「起動直後の連続送信が続く区間では11ビット時間ぶん後ろにずれ、バスが一度空いて以降は送信要求時刻どおりに戻る」という範囲に収まる（11ビット時間以外のずれは発生しない）。

## Assumptions

- 同期成立の判定に用いる「連続レセシブ期間」の長さは11ビット時間とする（ドメイン仕様書 FR-031aに準拠）。ビット時間はバスの通信速度から決まる既存の値を用いる。
- 電源投入時刻・初期化時間の既定値はどちらも 0 とする（ドメイン仕様書の未決事項 Q-5 の仮置き値を踏襲）。実機の実測値が判明した場合はノードごとの設定として与える。
- 既定値（0）の構成であっても同期検出（11ビット時間の観測）は省略しない。これにより既存機能001 のログの一部の時刻が11ビット時間分ずれるが、CAN の実挙動に忠実であることを優先し、後方互換のための「起動を省略するモード」は設けない（憲章 IV: 不要な分岐・互換用の仕組みを追加しない）。ずれの範囲は SC-006 のとおり、起動直後の連続送信区間に限定される。
- 起動記録の出力形式・ファイル名・保存先は実装方式を決める `/speckit.plan` 以降で確定する。本仕様は「起動記録に何が含まれるべきか」のみを規定する。
- 送信要求は起動状態にかかわらず設定された周期どおりに発生し、通常動作前のものは保留される（ドメイン仕様書 FR-031c の読みに従う）。その結果、保留中に次周期の要求が来た場合は既存機能001 の上書き規則がそのまま適用され、上書き回数が累積する。
- エラー状態制御（エラーアクティブ／パッシブ／バスオフ）とバスオフからの復帰は本機能のスコープ外とする。通常動作からバスオフへ遷移する経路は設けない（憲章 VI [P②] の「枠のみ」は別機能で扱う）。
- 本機能により、既存機能 001 の SC-004 における「送信開始可能になった時刻」は、各ノードの通常動作開始時刻として具体化される。
