# Phase 0 Research: ノードのスタートアップ制御

`spec.md` は「何を」だけを規定し、同期検出をフレーム単位 DES にどう載せるか、起動記録をどの形式で
出力するかを実装側に委ねている。本フェーズでその技術選定を確定する。

## 1. フレーム単位 DES における「11ビット連続レセシブ」の表現

- **Decision**: ビットを数えるのではなく、「レセシブ期間（recessive window）の開始時刻」を1つ追跡し、
  同期完了時刻を次式で算出する。

  ```
  windowStart   = max(検出開始時刻, 現在のレセシブ期間の開始時刻)
  syncComplete  = windowStart + 11 * ビット時間
  ```

  レセシブ期間の開始時刻は、フレームが送信中なら「そのフレームの送信完了時刻 − 8ビット時間」
  （ACKデリミタ1 + EOF7 = 8ビットが送信の末尾に現れるため）、送信がなければ直前のフレームの
  同じ時点、シミュレーション開始直後はシミュレーション開始時刻とする。

- **Rationale**: この1本の式で、ドメイン仕様書 FR-031a の2つのケースが自動的に両立する。
  - バスがアイドルのときに検出開始 → `syncComplete = 検出開始 + 11ビット時間`（FR-005 / SC-003）
  - 他ノードの送信中に検出開始 → レセシブ期間開始は `TxEnd − 8ビット`、したがって
    `syncComplete = TxEnd − 8ビット + 11ビット = TxEnd + 3ビット` ＝ **インターミッション終了時点**
    （FR-006 / SC-004）。ドメイン仕様書が「ACKデリミタ(1)＋EOF(7)＋インターミッション(3) の11ビット
    で成立する」と書いている内容とビット単位で一致する。
  - インターミッションの途中など、残りのレセシブが11ビットに満たない時点で検出を開始した場合も、
    `windowStart = 検出開始時刻` となり、次にドミナントが来た時点で不成立が確定する（FR-007）。
  ビット単位のシミュレーションを行わないという憲章 [P③] にも適合する。

- **Alternatives considered**:
  - ビット単位でレセシブを数える: 憲章 [P③]（イベントはフレーム単位）に真っ向から反し、
    イベント数が3〜4桁増える。
  - 「送信中に検出開始したら常にインターミッション終了で成立」と単純化する: インターミッション
    途中から検出を開始したケースで実際より早く同期してしまい、SC-004 とエッジケースが矛盾する。

## 2. レセシブ期間が途切れたときの同期完了イベントの扱い

- **Decision**: `EventQueue` に取り消し機構を追加せず、**遅延無効化（lazy invalidation）** を採る。
  各ノードに「現在有効な同期完了予定時刻」を1つ持たせ、送信が開始されるたびにバス同期検出中の
  全ノードについて予定時刻を再計算して新しいイベントを積む。同期完了イベントを処理するときに
  「ノードがまだバス同期検出中」かつ「イベントの時刻がノードの現在の予定時刻と一致する」ことを
  確認し、一致しなければ古いイベントとして破棄する。

- **Rationale**: 既存の `EventQueue`（ソート済みベクタ、Push/PopNext のみ）に手を入れずに済み、
  憲章 IV（不要な機構を足さない）に適合する。無効化されたイベントは高々「送信回数 × 同期検出中の
  ノード数（最大16）」であり、起動完了後は二度と積まれないため、イベント数は実質的に増えない。
  判定は決定的なので FR-014／SC-005（再現性）も維持される。

- **Alternatives considered**:
  - `EventQueue` にイベント ID と削除 API を追加: 削除が O(n) になり、ID の採番・保持という状態が
    増える。得られる利益（積まれるイベントが数個減る）に見合わない。
  - 同期判定を「バスアイドル」イベントの処理時にだけ行う: 送信要求が1件も発生しない構成では
    バスアイドルイベント自体が発生せず、ノードが永久に通常動作へ到達しない。破綻するため不採用。

## 3. 新しいイベント種別と同一時刻の処理順序

- **Decision**: イベント種別に `PowerOn` / `InitDone` / `SyncComplete` の3つを追加し、同一時刻の
  処理順序を次のとおりとする（既存の相対順序は変更しない）。

  ```
  TxComplete → IntermissionEnd → RxProcess → PowerOn → InitDone → SyncComplete → TxRequest → BusIdle → SimulationEnd
  ```

- **Rationale**: ドメイン仕様書 FR-013 が定める順序「送信完了 → インターミッション終了 → 受信処理
  → 電源投入・初期化完了 → 送信要求 → バスアイドル」に、起動系の遷移として `SyncComplete` を同じ
  グループの末尾に置いたもの。これにより、
  - インターミッション終了と同時に同期が成立したノードは、その直後の同じ時刻の「バスアイドル」
    による調停に**参加できる**（取りこぼしがない）。
  - 通常動作に入る前に発生した送信要求（`TxRequest`）は、同じ時刻でも `SyncComplete` の後に処理
    されるため、状態判定が一意に決まる。
  既存の種別どうしの相対順序は変えていないため、機能 001 で確認済みの挙動（調停順・上書き）は
  そのまま維持される。

  **実装上の注意**: 機能 001 では「バスが空いているときに送信要求が来たら調停を試みる」ために
  `TxRequest` の処理で `BusIdle` を積んでいる。本機能では同様に、**`SyncComplete` の処理でも、
  バスが空いていてそのノードに送信待ちがあれば `BusIdle` を積む**必要がある。これがないと、
  全ノードの送信要求が通常動作より前に発生し終えている構成（初回オフセット0など）で、通常動作へ
  移行しても調停の契機が一度も訪れず、1フレームも送信されない。

- **Alternatives considered**:
  - `SyncComplete` を `BusIdle` の後に置く: 同期成立と同時刻の調停に参加できず、最初の送信が
    1サイクル遅れる。SC-004（インターミッション終了時点で通常動作）の観測とずれる。

## 4. 起動記録の出力形式

- **Decision**: フレームログ・集計サマリと同じ規則で `<設定ファイル名>.startup.csv` として CSV
  （UTF-8、ヘッダ行あり）を出力する。1ノード1行、列は
  `Node_Id,Node_Name,Power_On_us,Init_Done_us,Normal_Entry_us,Reached_Normal`。

- **Rationale**: ドメイン仕様書 FR-053 が「スタートアップの状態遷移はフレームのログとは別の
  イベントログに出力する」と要求しており、別ファイルにするのが素直。形式・命名は機能 001 の
  `<設定ファイル名>.log.csv` / `.summary.csv` と揃えることで、UI 側の変更を不要にできる
  （憲章 IV）。通常動作に到達しなかったノードは `Reached_Normal=FALSE` とし `Normal_Entry_us` を
  空欄にすることで FR-013 を満たす。

- **Alternatives considered**:
  - 既存のフレームログに起動行を混ぜる: 列構成が全く異なり、機能 001 の
    `contracts/log-output-format.md` の契約を壊す。FR-053 にも反する。
  - 起動記録を UI にだけ表示する: ファイルとして残らず、再現性の検証（SC-005）が手作業になる。

## 5. 設定ファイルへのキー追加

- **Decision**: `[NodeN]` セクションに `PowerOnTimeUs` と `InitDurationUs`（いずれも任意、既定 0、
  0以上の整数）を追加する。既存キー（`NodeId` / `Name` / `RxFilter` / `ReceiveDelayUs`）と
  同じ命名・検証方針に揃える。

- **Rationale**: 機能 001 の設定形式（セクション区切りの `key=value`）をそのまま拡張でき、
  既存の構成ファイルは変更不要（省略時は既定 0）。外部ライブラリを増やさない方針も維持される。

- **Alternatives considered**:
  - 起動設定だけ別ファイルに分ける: 構成が2ファイルに割れ、利用者の管理コストだけが増える。

## 6. 機能 001 の成果物への影響の扱い

- **Decision**: 本機能の実装により機能 001 のログは全時刻が一律11ビット時間だけ後ろへずれるため、
  機能 001 の成果物を次の方針で更新する（本機能のタスクに含める）。
  - `quickstart.md`（実際の実行結果に対する期待値）: 起動オフセットを含んだ実挙動の値へ**書き換える**。
  - `contracts/log-output-format.md` の例示 CSV: この例はドメイン仕様書 FR-054 のログ例をそのまま
    引いたものなので数値は**書き換えず**、「機能 002 適用後の実行では各時刻に起動待ち時間
    （11ビット時間）が加わる」旨の**注記を追加**する。

- **Rationale**: 憲章 V（ドキュメントとの同期）は実態と乖離した成果物を残さないことを要求するが、
  ドメイン仕様書から引用した例まで書き換えると、今度は一次情報源との対応が取れなくなる。
  「実測値に基づく期待値は更新、引用は注記」で両方の整合を保てる。`spec.md` SC-006 が「ずれるのは
  時刻のみで、送信順序・調停結果・送信回数は変わらない」ことを保証しているため、更新は機械的。

- **Alternatives considered**:
  - 機能 001 の成果物をすべて凍結し注記だけ加える: quickstart の期待値が実行結果と食い違い、
    次に検証する人が失敗と誤認する。
  - 例示 CSV も含めてすべて書き換える: ドメイン仕様書 FR-054 の引用である旨の対応が崩れる。
