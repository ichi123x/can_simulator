# Research: ビットスタッフィングを CAN 2.0A の規格どおりに数える

## R1. スタッフビットの数え方

- **Decision**: SOF〜CRC シーケンスのビット列を先頭から読み、スタッフビットを実際に差し込んだ新しい列（差し込んだビット列。計算用のフレームバッファ）に 1 ビットずつ書き足す。書き足した列の末尾で同じ値が 5 個続いたら、反対の値のビットを 1 つ書き足して、連続の数を 1（書き足したスタッフビット）に戻す。スタッフビットの数 = 書き足した列の長さ − 元の列の長さ。
- **Rationale**: Bosch CAN 2.0A §5 は「送信側は同じ値が 5 ビット続いたら、反対の値のビットを 1 つ差し込む」と定め、差し込んだビットも後続の 5 連続の判定に含まれる。差し込んだ列の上で数えれば、この決まりがそのまま実装になり、今の誤り（差し込んだ直後のビットを元の列の直前のビットと比べ、連続の 2 個目と数える）は構造的に起きない。ドメイン仕様書 FR-021 の「実際のビット列にビットスタッフィングを適用したビット数」とも言葉が一致する。
- **Alternatives considered**:
  - 今の数え方のまま、差し込んだときに「直前の値」を反対の値に置き換える（数行の修正）。結果は同じになるが、列を作らないので「どこに差し込んだか」を確かめにくく、説明もしにくい。利用者の意向（CAN 仕様に寄り添った説明しやすい実装、2026-10-13）に合わないので採らない。
  - 最悪値の式 ⌊(34 + 8 × DLC − 1) / 4⌋ を使う。実際のビット列によらない上限で、FR-021 に反するので採らない。

## R2. 差し込んだビット列を外に見せるか

- **Decision**: 見せない。`ComputeFrameTiming` の結果（`FrameTimingResult`: 総ビット数・スタッフビット数・ビット時間・伝送時間・インターミッション）だけを今までどおり返す。差し込んだ列は関数の中の作業用。
- **Rationale**: 画面にも CSV にもビット列は出さないので、公開しても使う所が無い（憲章 IV）。テストは総ビット数とスタッフビット数を、別に書いたスクリプトで規格どおりに数えた値と照合すれば、差し込む位置の誤りも数の違いとして検出できる（全 ID × DLC 0〜8 の照合、SC-003）。
- **Alternatives considered**: ビット列を返す関数を追加して、差し込んだ位置をテストで直接確かめる。将来ビット列を画面に出す要望が出たときに追加すればよい。

## R3. 伝送時間の事前計算（FR-006）

- **Decision**: `SimulationEngine` のコンストラクタ（実行の開始時）で、全ノードの全フレームの定義について `ComputeFrameTiming(CanId, Dlc, Data, BitRateBps)` を 1 回ずつ呼び、結果をノード・フレームの番号で引ける表に持つ。送信を始めるとき（今 `ComputeFrameTiming` を呼んでいる所）は、この表を引く。
- **Rationale**: フレームのビット列は ID・DLC・データ（定義の 0xFF）で決まり、実行中に変わらない。送信待ちの間の更新（FR-011・Update_Count）でも、データは定義と同じ 0xFF のまま（機能 006 FR-014）。表を引けば、送信のたびの CRC とスタッフの計算が無くなり、重い構成でも速くなるか、少なくとも遅くならない。結果は送信のたびに計算した場合と同じ。
- **Alternatives considered**:
  - 今までどおり送信のたびに計算する。正しさは同じだが、利用者の提案（実行の開始時に計算しておく）と FR-006 の意図に合わない。
  - 送信待ちのフレームのデータ（`PendingFrame::CurrentData`）から計算する今の形を残す。データを模擬しない方針（2026-10-13）では定義のデータと常に同じなので、定義から計算すれば足りる。

## R4. 影響を受ける既存のテスト

- **Decision**: 機能 030 の `tests/` で、伝送時間の値に依存する期待値を洗い出し、規格どおりの値に直す。調べた範囲では、`feature_001_tests.cpp` は総ビット数の構成（34 + 8 × DLC + スタッフ + 10）とスタッフビット数の範囲（0〜24）を確かめるだけで、具体的なビット数を持たないので、そのまま通る見込み。`feature_007_tests.cpp` は「ログの伝送時間 = `ComputeFrameTiming` の伝送時間」の関係を確かめるので、そのまま通る。基準 CSV との比較（004 SC-009・008 SC-005）は `CANSIM_BASELINE_DIR` を設定したときだけ走り、基準は本機能の後のビルドで作り直す（`tools/cansim_runner/README.md` の手順）。
- **Rationale**: 本機能は値を変えることが目的なので、値に依存する期待値は直すのが正しい（SC-008）。どの期待値を直したかは tasks.md と実装の報告で示す。
- **Alternatives considered**: 期待値を直さずに古い値のまま残す。規格と合わない値を正しいとして固定することになるので採らない。

## R5. 文書の数値

- **Decision**: サンプルの実行結果の数値を書いた文書を、本機能の後の実行結果で書き直す。対象: `tools/vehicle_samples/README.md` の結果の表（送信フレーム・ログの行・調停負けの再送・最長の待ち・バス負荷）と 16 ECU の詳細、`README.md` の「バス使用率」「再送フレーム数」、CLAUDE.md の SampleConfigs の説明（16 ECU の 4,015 フレーム・再送 990・バス負荷 約 3〜19%）。
- **Rationale**: 憲章 V（ドキュメントとの同期）。伝送時間が短くなるので、バス負荷・待ち時間・再送の数が変わる。送信フレーム数（送信の回数）は、バスが詰まって送信が抜けない限り変わらない。
- **Alternatives considered**: 文書に「機能 031 の前の値」と注記して残す。読み手が古い値を使うおそれがあるので、新しい値に書き直す。

## R6. 手計算の値の確かめ方

- **Decision**: 規格の定義（SOF・ID・RTR・IDE・r0・DLC・データ・CRC-15、5 連続で反対のビットを差し込み、差し込んだビットも数える、末尾の 10 ビットはスタッフしない）を、製品のコードとは別の Python のスクリプトで書き、SC-001 の 5 例の値を求めてテストにリテラルで書く。全 ID × DLC 0〜8 の照合（SC-003）は、テストの中に規格の定義どおりの独立した数え方（参照の実装）を短く書いて比べる。
- **Rationale**: 製品のコードと同じ計算式をテストで繰り返すと、同じ誤りを見逃す。SC-001 の値はドメイン仕様書のログの例（0x080 = 123 ビット・スタッフ 15）とも一致することを確かめた（2026-10-13）。参照の実装は「差し込んだ列の末尾を見る」製品の方法とは別の書き方（元の列を読みながら、直前に出力したビットの値と連続の数を持つ）にする。
- **Alternatives considered**: 全組み合わせの期待値をファイルに持つ。18,432 通りの表は読みにくく、根拠の説明にならないので採らない。
