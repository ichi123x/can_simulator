# Feature Specification: ビットスタッフィングを CAN 2.0A の規格どおりに数える

**Feature Branch**: `ver.0.9`（仕様の連番 031）

**Created**: 2026-10-13

**Status**: Draft

**Input**: User description: "フレームの伝送時間の計算で、ビットスタッフィングを CAN 2.0A の規格どおりに数えるように直す（機能 031）。現状はスタッフビットを実際のビット列に差し込まず、元のビット列どうしで連続を数え続けるため、同じ値が続く区間で 2 個目以降のスタッフビットを多く数える。スタッフビットを実際に差し込んだビット列の上で 5 連続を調べる形にする。データの中身は模擬せず、データは常に DLC 分の 0xFF のまま。伝送時間はフレームの定義ごとに実行開始時に 1 回計算してよい。CAN 仕様に寄り添った実装の方が、エージェントにも顧客にも説明しやすい。"

## 背景

ドメイン仕様書（`Doc/CANバスシミュレータ仕様.md`）の FR-021 は、フレームの伝送時間を「実際のビット列（CRC を含む）にビットスタッフィング（同一レベル 5 ビット連続で反転ビット 1 つ挿入、SOF〜CRC シーケンス）を適用したビット数 × ビット時間」と定めている。同じ仕様書のログの例では、データがオール 1 の ID 0x080・DLC 8 のフレームを「123 ビット（スタッフビット 15）で 246 µs」としている。

現在のシミュレータは、スタッフビットを差し込んだ後も、差し込む前の元のビット列どうしで同じ値の連続を数え続ける。そのため、差し込んだ直後のビットを連続の 1 個目ではなく 2 個目と数え、同じ値が続く区間では 2 個目以降のスタッフビットを 5 ビットごとではなく 4 ビットごとに数えてしまう。結果として、上の 0x080 のフレームを 127 ビット（スタッフビット 19）、254 µs と計算しており、仕様書の値と合わない。誤りはスタッフビットを多く数える向きだけで、少なく数えることはない。

本機能は、スタッフビットの数え方を規格（Bosch CAN Specification 2.0 Part A §5）と仕様書 FR-021 のとおりに直す。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - シミュレーションの伝送時間が規格どおりになる (Priority: P1)

利用者はシミュレーションを実行し、フレームログの送信開始から送信完了までの時間（伝送時間）が、CAN 2.0A の規格どおりにスタッフビットを入れたビット数 × ビット時間になっていることを確かめる。顧客やエージェントに結果を説明するとき、「規格どおりに計算している」と言える。

**Why this priority**: 伝送時間は、送信完了・受信の時刻、送信待ち時間、バス負荷など、シミュレーションのほぼすべての結果の元になる。ここが規格と合わないと、他のすべての数値の説明がつかない。

**Independent Test**: 仕様書のログの例と同じ構成（ID 0x080 と 0x100、DLC 8、500 kbps、同時に送信要求）を実行し、フレームログの 0x080 の伝送時間が 246 µs、0x100 の送信開始が 0x080 の送信完了の 6 µs 後で、0x100 の伝送時間も 246 µs であることを確かめる。

**Acceptance Scenarios**:

1. **Given** ID 0x080・DLC 8（データはオール 1）のフレームを 500 kbps で送る構成、**When** シミュレーションを実行する、**Then** フレームログのそのフレームの送信開始から送信完了までが 246 µs（123 ビット × 2 µs）になる。
2. **Given** 0x080 と 0x100（どちらも DLC 8）が同時に送信を要求する構成（仕様書のログの例と同じ）、**When** 実行する、**Then** 0x100 は 0x080 の送信完了の 6 µs（インターミッション 3 ビット）後に送信を始め、その伝送時間も 246 µs になる。
3. **Given** 同じ構成、**When** 2 回実行する、**Then** フレームログ・集計・起動記録が完全に一致する。

---

### User Story 2 - 入力画面のビット長・伝送時間が規格どおりになる (Priority: P2)

利用者はデータフレーム編集の追加・編集の入力画面で ID と DLC を入れ、表示される「ビット長（スタッフビット込み）」と「伝送時間」が、規格どおりの値になっていることを確かめる。フレームを登録する前に、バス負荷の見当を正しくつけられる。

**Why this priority**: 入力画面の表示はシミュレーションと同じ計算を使うので、User Story 1 を直せば同じ値になる。表示だけの確認なので P2 とする。

**Independent Test**: 入力画面で ID 0x080・DLC 8 を入れ、500 kbps のプロジェクトでビット長 123 ビット・伝送時間 246 µs と表示されることを確かめる。

**Acceptance Scenarios**:

1. **Given** 通信速度 500 kbps のプロジェクトの入力画面、**When** ID 0x080・DLC 8 を入れる、**Then** ビット長 123 ビット・伝送時間 246 µs と表示される。
2. **Given** 同じ入力画面、**When** ID 0x7FF・DLC 0 を入れる、**Then** ビット長 47 ビット・伝送時間 94 µs と表示される（本機能の前と同じ値）。

---

### User Story 3 - 結果の説明がつく（既存の結果との差がわかる） (Priority: P3)

利用者は、本機能の前に出したサンプルの結果と、本機能の後の結果を比べ、変わったのは伝送時間（とそれに伴う時刻・負荷・待ち時間）だけで、送信の順序・調停の結果・送信の回数などは変わっていないことを確かめる。

**Why this priority**: 計算の修正で結果が変わる理由を説明できることは大切だが、機能そのものは User Story 1 で完結している。

**Independent Test**: 本機能の前と後で同じサンプルを実行し、フレームログの行数・行の順序・CAN ID・送信 ECU・受信 ECU・状態・再送回数・更新回数を比べる。

**Acceptance Scenarios**:

1. **Given** バスが空いていて調停の起きない構成（各フレームの間が十分に空いている）、**When** 本機能の前と後で実行する、**Then** 行数・行の順序・CAN ID・送信 ECU・受信 ECU・状態・再送回数・更新回数・送信要求時刻・送信開始時刻は変わらず、送信完了時刻と受信の時刻が、そのフレームのスタッフビットの差 × ビット時間だけ早くなる（同じ値の続かないフレームでは変わらない）。バス負荷率（`Bus_Load_Pct`）は、バスの使用時間が減る分だけ同じか小さくなる。
2. **Given** 同じ構成、**When** 本機能の前と後の集計（`.summary.csv`）を比べる、**Then** 伝送時間・総送信レイテンシ・バス負荷率は同じか小さくなり、送信待ち遅延（QueueingDelay）・ジッターは変わらない。

---

### Edge Cases

- 同じ値の続かないフレーム（例: ID 0x7FF・DLC 0、ID 0x123・DLC 8・データ 01〜08）は、本機能の前と同じビット数になる。
- 1 つのフレームの中で、差し込んだスタッフビットとその後の元のビットで再び同じ値が 5 個続く場合（例: 1 が 5 個続いて 0 を差し込んだ後に、元のビットの 0 が 4 個続く）は、差し込んだビットも数えに入れて、もう 1 つスタッフビットを差し込む。
- スタッフの対象は SOF から CRC シーケンスの終わりまで。CRC デリミタ・ACK スロット・ACK デリミタ・EOF（合わせて 10 ビット）にはスタッフしない。CRC シーケンスの最後のビットで 5 連続になった場合も、規格どおりスタッフビットを 1 つ入れる。
- インターミッション（3 ビット）は伝送時間に含めない（今までどおり）。
- 通信速度（125k / 250k / 500k / 1M bps）によらず、ビット数は同じで、伝送時間はビット数 × ビット時間になる。
- 調停の負け・再送・送信バッファの満杯（OVERWRITE）の扱いは変わらない。再送されたフレームの伝送時間は、最初の送信と同じ。
- バスが連続して埋まっている区間では、各フレームの伝送時間が短くなる分、後に続くフレームの送信開始も早くなる。そのため調停の組み合わせが変わり、行の順序や再送回数が本機能の前と変わることがある（計算が規格に近づいた結果であり、誤りではない）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、フレームのビット数を、SOF から CRC シーケンスの終わりまでのビット列に、規格どおりのビットスタッフィングを適用して求めなければならない。同じ値が 5 ビット続いたら、その直後に反対の値のビットを 1 つ差し込み、差し込んだビットも、その後の同じ値の連続を数えるときの 1 個目に数える（Bosch CAN 2.0A §5、ドメイン仕様書 FR-021）。
- **FR-002**: システムは、フレームの総ビット数を「スタッフビットを差し込んだ後の SOF〜CRC シーケンスのビット数 + 10（CRC デリミタ・ACK スロット・ACK デリミタ・EOF）」とし、伝送時間を「総ビット数 × ビット時間」としなければならない。インターミッション 3 ビットは伝送時間に含めない。
- **FR-003**: システムは、フレームのビット列を、ID・DLC・データ（DLC 分の 0xFF）・CRC-15（生成多項式 x^15 + x^14 + x^10 + x^8 + x^7 + x^4 + x^3 + 1）から作らなければならない（今までどおり）。データの中身を利用者が指定する手段は持たない。
- **FR-004**: システムは、FR-001・FR-002 で求めた伝送時間を、シミュレーションの送信完了時刻（およびそれに続く受信の時刻・送信待ち時間・バス負荷の計算）と、データフレーム編集の入力画面の「ビット長」「伝送時間」の表示の両方に使わなければならない。
- **FR-005**: システムは、同じ構成から常に同じ結果（フレームログ・集計・起動記録）を出さなければならない。
- **FR-006**: システムは、伝送時間をフレームの定義ごとに実行の開始時に 1 回計算し、そのフレームの送信のたびに同じ値を使わなければならない（フレームのビット列は ID・DLC・データで決まり、実行中に変わらないため）。
- **FR-007**: 本機能は、スタッフビットの数え方以外（フレームの形式、CRC、調停・再送・バッファ・起動制御の動作、ログ・集計の列）を変えてはならない。

### Key Entities *(include if feature involves data)*

- **フレームのビット列**: 1 つのフレームの定義（ID・DLC・データ 0xFF）から作る、SOF から EOF までのビットの並び。スタッフビットを差し込んだ後の並びと、その中のスタッフビットの数を持つ。
- **フレームの伝送時間**: ビット列の総ビット数 × ビット時間。フレームの定義と通信速度で決まる。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 次のフレームで、総ビット数・スタッフビット数・伝送時間が、規格の定義から手で数えた値と完全に一致する（500 kbps）。

  | フレーム | 総ビット数 | スタッフビット | 伝送時間 |
  |---|---|---|---|
  | ID 0x000・DLC 0 | 50 | 6 | 100 µs |
  | ID 0x7FF・DLC 0 | 47 | 3 | 94 µs |
  | ID 0x555・DLC 1・データ 0xAA | 54 | 2 | 108 µs |
  | ID 0x123・DLC 8・データ 01〜08 | 116 | 8 | 232 µs |
  | ID 0x080・DLC 8・データ 0xFF | 123 | 15 | 246 µs |

- **SC-002**: ドメイン仕様書のログの例（0x080 と 0x100、DLC 8、500 kbps、同時に送信要求）と同じ構成で、0x080 と 0x100 の伝送時間がどちらも 246 µs、0x100 の送信開始が 0x080 の送信完了の 6 µs 後になる。
- **SC-003**: ID 0x000〜0x7FF の全 ID と DLC 0〜8 のすべての組み合わせ（データは 0xFF）で、スタッフビット数が、規格の定義どおりに独立に数えた値と一致する（過少も過大も 0 件）。
- **SC-004**: SC-003 のすべての組み合わせで、スタッフビット数がドメイン仕様書の最悪値 ⌊(34 + 8 × DLC − 1) / 4⌋ を超えない。
- **SC-005**: 通信速度 125k / 250k / 500k / 1M bps のそれぞれで、伝送時間が総ビット数 × ビット時間（8 / 4 / 2 / 1 µs）と一致する。
- **SC-006**: 同じ構成で 2 回実行したとき、フレームログ・集計・起動記録が完全に一致する。
- **SC-007**: 調停の起きない構成で、本機能の前と後のフレームログを比べたとき、送信完了時刻・受信の時刻・バス負荷率以外の列が一致し、送信完了時刻の差がそのフレームのスタッフビットの差 × ビット時間に等しく、バス負荷率は前の値以下である。
- **SC-008**: 既存の自動テスト（機能 030 の GoogleTest と `tools/cansim_runner` の checks）が、本機能で値が変わる項目の期待値を規格どおりの値に直したうえで、すべて通る。

## Assumptions

- データの中身は模擬しない（利用者決定 2026-10-13）。データは機能 006 のとおり常に DLC 分の 0xFF とする。実際のデータの値に応じた伝送時間の変化は対象外で、扱うには CPU やアプリケーションのタイミングの模擬が必要になる。
- 0xFF は 1 が続くのでスタッフビットが多めに入る側の値であり、実際のデータより伝送時間を短く見積もることは起きにくい。
- 物理層（ビットタイミング・伝搬遅延・同期のずれ）は今までどおり模擬しない（憲章 VI の P④）。
- エラーフレーム・オーバーロードフレーム・リモートフレームは対象外（憲章 VI の P①）。
- 伝送時間が短くなるので、サンプルプロジェクトの結果（CSV）、`tools/cansim_runner` の基準 CSV、既存のテストで伝送時間に依存する期待値は変わる。これらは本機能の中で規格どおりの値に作り直す。CLAUDE.md や README に記載した実行結果の数値（サンプルのフレーム数・再送数・バス負荷など）も、変わったものは同じ作業の中で更新する。
- 手計算の値は、規格の定義を製品のコードとは別に書いた計算（例: 別の言語の短いスクリプト）で確かめた値とする。SC-001 の値は 2026-10-13 にこの方法で求めた。
