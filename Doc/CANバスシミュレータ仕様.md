## 1. 概要とスコープ

### 1.1 目的
最大16ノードが1本の CAN バスに接続されたネットワークを、ソフトウェアだけで模擬する。フレームの送信、調停、受信の時刻をログに残し、バス負荷率、送信待ち遅延、エンドツーエンドのレイテンシ、ジッターを評価できるようにする。

### 1.2 基本方針
- プロトコルは CAN 2.0A に準拠する。**[P①]**
- ノードの状態遷移は、スタートアップ制御、メッセージ送信制御（送信・調停）、エラー状態制御の3つからなる。**[P②] [状態遷移]**
- シミュレーション方式はイベント駆動型（Discrete Event Simulation, DES）とする。**[P③]**
- 通信仕様とログ仕様は [性能・ログ] に従う。**[P④]**
- 接続ノード数は最大16とする。**[P⑤]**
- 電気的な物理層（差動電圧、終端抵抗、伝搬遅延、ビットタイミング、クロック誤差）は模擬しない。全ノードは理想的に同期しているとみなす。**[既定]**

### 1.3 スコープ

| 区分 | 対象 |
|---|---|
| 対象（初期版） | CAN 2.0A 標準フォーマット（11ビットID、データ0〜8バイト）のデータフレーム、ID による調停、自動再送信、スタートアップ制御、ビットスタッフィングを含む伝送時間の計算、[性能・ログ] 形式のログ、評価指標の算出 |
| 枠だけ用意（中身は初期版では搭載しない） | エラー状態制御（エラーアクティブ／パッシブ／バスオフ、TEC/REC）、エラー発生の入口 **[決定]** |
| 対象外（初期版） | 拡張フォーマット（29ビットID）、CAN FD（64バイト）**[決定]**、リモートフレーム、オーバーロードフレーム **[既定]**、物理層、実機との接続 |

## 2. ユーザーシナリオとテスト

### US-1 ネットワークを構成してシミュレーションを実行する（P1）
利用者は、ノード（最大16）と各ノードの送信フレーム一覧を設定ファイルで与え、指定した時間だけシミュレーションを実行できる。
- 受け入れシナリオ
  1. **前提** [図] と同じ6ノード・500 kbps の構成、**操作** 10秒実行、**結果** 全ノードがスタートアップを終えたあと、各フレームが周期どおりに送信され、ログに記録される。
  2. **前提** 17ノードの構成、または同じIDを2ノードが送信する構成、**操作** 読み込み、**結果** 構成エラーとして拒否され、理由が表示される。

### US-2 調停と再送信を確認する（P1）
- 受け入れシナリオ
  1. **前提** ID 0x080 と 0x100 が同じ時刻に送信要求、**操作** 実行、**結果** 0x080 が先に送信され、0x100 は 0x080 の EOF とインターミッションのあとに送信される。0x100 のログ行には調停負けと再送信回数1が記録される。

### US-3 性能指標を評価する（P1）
- 受け入れシナリオ
  1. **操作** 実行後にログを集計、**結果** [性能・ログ] の4つの指標（総送信レイテンシ、送信待ち遅延、フレーム伝送時間、バス負荷率）と、ジッターが算出できる。

### US-4 スタートアップを確認する（P2）
- 受け入れシナリオ
  1. **前提** ノードごとに電源投入時刻をずらした構成、**操作** 実行、**結果** 各ノードが「電源投入 → 初期化 → 11ビット連続レセシブ検出 → 通常動作」を経て送信を始め、通常動作に入った時刻がログに残る。

### US-5 （将来）エラーを発生させて状態遷移を確認する（P3）
初期版では枠だけ用意する **[決定]**。エラー発生の入口と状態の枠があり、将来の版でエラー注入を実装できること。

### エッジケース
- 送信要求の時点でバスが他ノードの送信中である場合（→ FR-032）
- 送信待ちの間に同じフレームの次の周期が来た場合（→ FR-024）
- 同じ時刻に複数のイベントが起きる場合（→ FR-013）
- バス負荷率が 100% に近く、低優先度のフレームが送信できない状態（飢餓）

## 3. 機能要件

### 3.1 ネットワークとノード
- **FR-001** バスは1本とする。通信速度は既定 500 kbps（1ビット = 2 µs）とし、設定で変更できる（125 k / 250 k / 500 k / 1 Mbps）。**[図] [既定]**
- **FR-002** 接続ノード数は1〜16とする。17以上の構成は読み込み時に拒否する。**[P⑤]**
- **FR-003** 既定の構成は [図] の6ノード（ECU1 エンジン制御、ECU2 トランスミッション、ECU3 ABS/ブレーキ、ECU4 ボディ制御、ECU5 メータークラスタ、ECU6 エアバッグ）とし、付録Aのサンプルフレームを置く。**[図] [既定]**
- **FR-004** 各ノードは送信フレーム一覧を持つ。各エントリは ID（11ビット）、DLC（0〜8）、DLC 分のデータ、送信周期、初回オフセットを持つ。データのバイト数が DLC と合わない構成は拒否する。**[既定]**（リセット前の決定を引き継ぐ。**[要確認 Q-1]**）
- **FR-005** 1つの ID を送信するノードは1つに限る。違反した構成は読み込み時に拒否する。**[既定]**
- **FR-006** 各ノードは受信フィルタ（受信する ID の集合）を持つ。未指定時は全 ID を受信する。**[既定]**
- **FR-007** 各ノードは受信処理遅延（受信完了から受信アプリが処理を始めるまでの時間）を持つ。既定は固定値 0 µs とする。**[既定] [要確認 Q-3]**
- **FR-008** 構成は設定ファイルで与える。形式は未決。**[要確認 Q-2]**

### 3.2 イベント駆動シミュレーション（DES）
- **FR-010** シミュレーションは、時刻順に並んだイベントを1つずつ取り出して処理する DES とする。**[P③]**
- **FR-011** イベントはフレーム単位の区切りで起こす（ビットごとには起こさない）。**[決定]** イベントの種類は次のとおり。**[既定]**

  | イベント | 内容 |
  |---|---|
  | 電源投入 | ノードのスタートアップを開始する |
  | 初期化完了 | ノードが INIT モードを終え、バス同期の検出に入る |
  | 送信要求 | 送信フレーム一覧の周期で、送信要求が発生する |
  | バスアイドル（送信開始） | バスが空いた時点。送信待ちのノードがあれば SOF を出し、調停を決着させる |
  | 送信完了（EOF） | 勝ったフレームの EOF が終わる。受信ノードの受信も完了する |
  | インターミッション終了 | 3ビットのインターミッションが終わり、バスアイドルになる |
  | 受信処理 | 受信ノードのアプリがデータを取り出す（受信完了＋受信処理遅延） |
  | エラー（枠のみ） | 初期版では発生させない（FR-061） |
  | 終了 | シミュレーションを終える |

- **FR-012** 時間は内部では ns 単位の整数で持ち、ログには µs 単位で出力する。**[既定]**（1ビット時間が µs の整数にならない速度に備える）
- **FR-013** 同じ時刻のイベントは、次の順で処理する: 送信完了 → インターミッション終了 → 受信処理 → 電源投入・初期化完了 → 送信要求 → バスアイドル（送信開始）。同じ種類の中ではノード番号の小さい順とする。これにより、同じ構成からは必ず同じ結果が得られる。**[既定]**
- **FR-014** シミュレーションは指定したシミュレーション時間で終了する。**[既定]**
- **FR-015** シミュレーション時間は実時間と同期させず、できるだけ速く進める。**[既定]**

### 3.3 フレーム
- **FR-020** データフレームは CAN 2.0A 標準フォーマットとする: SOF(1) / ID(11) / RTR(1) / IDE(1) / r0(1) / DLC(4) / データ(0〜64ビット) / CRC(15) / CRCデリミタ(1) / ACKスロット(1) / ACKデリミタ(1) / EOF(7)。**[P①] [Bosch §3.1.1]**
- **FR-021** フレームの伝送時間は、実際のビット列（CRC を含む）にビットスタッフィング（同一レベル5ビット連続で反転ビット1つ挿入、SOF〜CRCシーケンス）を適用したビット数 × ビット時間とする。**[Bosch §5] [既定]**
- **FR-022** フレームのあとにインターミッション3ビットを置く。この間は新しい送信を始めない。**[Bosch §3.1.5]**
- **FR-023** CRC は生成多項式 x^15 + x^14 + x^10 + x^8 + x^7 + x^4 + x^3 + 1 で計算する。初期版では伝送時間（スタッフビット数）を求めるためにだけ使う。**[Bosch §3.1.1] [既定]**
- **FR-024** 送信待ちの間に同じフレームの次の周期の送信要求が来た場合は、データを最新値で上書きし、上書き回数を数える。送信要求時刻（Tx_Request）は最初の要求の時刻のまま残す。**[既定] [要確認 Q-4]**

### 3.4 状態遷移: スタートアップ制御 [P②] [状態遷移 p.2]
- **FR-030** 各ノードは次の状態を遷移する。

  | 状態 | 次の状態へ移る条件 |
  |---|---|
  | 電源オフ／リセット | 電源投入時刻になった |
  | 初期化モード（INIT） | 初期化時間が経過した（レジスタ設定の完了とみなす） |
  | バス同期検出 | バス上で11ビット連続のレセシブを検出した |
  | 通常動作モード（Normal） | （以後、送信・受信を行う）。バスオフへの遷移は枠のみ（FR-061） |

- **FR-031** 電源投入時刻と初期化時間はノードごとに設定できる。既定はどちらも 0 とする。**[既定] [要確認 Q-5]**
- **FR-031a** 11ビット連続レセシブの検出は、バスがアイドルなら検出開始から11ビット時間後とする。他ノードの送信中に検出を始めた場合は、そのフレームの ACKデリミタ(1)＋EOF(7)＋インターミッション(3) の11ビットで成立するとみなし、インターミッション終了時点で通常動作に入る。**[既定]**
- **FR-031b** 通常動作に入った時刻をノードごとに記録する（[状態遷移 p.2] の Fast Startup 要求の確認に使う）。**[既定]**
- **FR-031c** 通常動作に入る前に発生した送信要求は、通常動作に入ったあとに送信する。**[既定]**

### 3.5 状態遷移: メッセージ送信制御 [P②] [状態遷移 p.1]
- **FR-032** 各ノードの送信は、次の5状態を遷移する。

  | 状態 | 次の状態 | 条件 |
  |---|---|---|
  | アイドル | 送信・調停中 | 送信要求があり、バスがアイドル |
  | アイドル | 自動再送信準備 | 送信要求があるが、バスが他ノードの送信中 **[既定]**（図にない経路） |
  | 送信・調停中 | データ送信・完了 | 調停に勝った |
  | 送信・調停中 | 調停負け・待機 | 調停に負けた |
  | データ送信・完了 | アイドル | EOF まで送信し、送信が成功した |
  | 調停負け・待機 | 自動再送信準備 | 勝ったフレームの EOF を検出した |
  | 自動再送信準備 | 送信・調停中 | インターミッション後、バスがアイドルになった（自動再送信） |

- **FR-033** 調停は「バスアイドル（送信開始）」イベントで決着させる。その時点で送信待ちフレームを持つ通常動作のノードのうち、先頭フレームの ID が最小のノードが勝つ。ビットごとの比較は行わず、調停で負けたビット位置も求めない。**[決定]**（全ノードが同期している前提で、ビット単位の非破壊調停 [Bosch §2] と同じ結果になる）
- **FR-034** 調停に負けたノードは、そのフレームの再送信回数を1増やして待機に入る。バスの占有時間には何も加えない。**[決定]**
- **FR-035** 1つのノードに送信待ちフレームが複数ある場合は、ID の小さい順に調停へ出す。**[既定]**（実際のコントローラの送信バッファ構成に依存。**[要確認 Q-4]**）
- **FR-036** 送信が成功すると ACK は必ず返るものとする（初期版ではエラーが起きないため）。**[決定（エラーは枠のみ）]**

### 3.6 状態遷移: エラー状態制御（枠のみ） [P②] [状態遷移 p.3]
- **FR-060** 各ノードはエラー状態（エラーアクティブ／エラーパッシブ／バスオフ）と、送信エラーカウンタ（TEC）、受信エラーカウンタ（REC）を持つ。初期版では常にエラーアクティブ、TEC = REC = 0 のままとする。**[決定]**
- **FR-061** 「エラー」イベントの入口（対象ノード、エラー種別、発生時刻）と、状態遷移の枠（TEC または REC > 127 でパッシブ、TEC > 255 でバスオフ、128×11ビットのレセシブ検出で復帰）を用意するが、初期版ではエラーを発生させない。**[決定] [状態遷移 p.3]**
- **FR-062** ログの Status には、将来のエラー記録用の値を予約しておく。**[決定] [性能・ログ]**

### 3.7 受信
- **FR-040** 送信が成功したフレームは、送信ノード以外の通常動作中のノードのうち、受信フィルタに合致するノードがすべて受信する。**[既定]**
- **FR-041** 受信開始時刻は送信開始時刻（SOF）と同じ、受信完了時刻は送信完了時刻（EOF の終わり）と同じとする。**[性能・ログ]**（単一ロガーでは同一、との記載に従う）
- **FR-042** 受信処理時刻は、受信完了時刻＋そのノードの受信処理遅延（FR-007）とする。**[既定]**

### 3.8 ログ [P④] [性能・ログ]
- **FR-050** ログは1フレーム×受信ノードで1行とする。受信ノードがないフレームも、送信側の情報だけで1行出す。**[決定]**
- **FR-051** 各行の項目は次のとおり。時刻はすべてシミュレーション開始からの µs とする。

  | 項目 | 内容 |
  |---|---|
  | Timestamp_us | 行を出した時刻（受信処理時刻。受信ノードがない行は送信完了時刻）**[既定]** |
  | CAN_ID | 16進（0x000〜0x7FF） |
  | DLC | 0〜8 |
  | Tx_Node / Rx_Node | 送信ノード番号、受信ノード番号 **[既定]**（[性能・ログ] にない追加項目） |
  | Tx_Request | 送信要求時刻 |
  | Tx_Start | 送信開始時刻（調停に勝った試行の SOF）**[既定]** |
  | Tx_End | 送信完了時刻（EOF の終わり） |
  | Rx_Start / Rx_End | 受信開始時刻、受信完了時刻 |
  | Rx_Process | 受信処理時刻 |
  | Bus_Load_Pct | Tx_End までの直前の計算ウィンドウでのバス負荷率 |
  | Status | SUCCESS、または ARBITRATION_LOST_RETRY（1回以上調停に負けた）。エラー用の値は予約のみ |
  | Retry_Count | 調停負けによる再送信回数 **[既定]** |
  | Overwrite_Count | 送信待ち中に上書きされた回数（FR-024）**[既定]** |

- **FR-052** 出力形式は CSV とする。JSON Lines 形式でも出力できるようにする。**[性能・ログ] [既定] [要確認 Q-6]**
- **FR-053** スタートアップの状態遷移（FR-031b）は、フレームのログとは別のイベントログに出力する。**[既定]**
- **FR-054** ログの例（500 kbps、ECU3 の 0x080 と ECU1 の 0x100 が同時に送信要求。受信処理遅延は ECU1 が 40 µs、ECU5 が 100 µs の構成）**[既定]**

  ```
  Timestamp_us,CAN_ID,DLC,Tx_Node,Rx_Node,Tx_Request,Tx_Start,Tx_End,Rx_Start,Rx_End,Rx_Process,Bus_Load_Pct,Status,Retry_Count,Overwrite_Count
  10000290,0x080,8,3,1,10000000,10000000,10000250,10000000,10000250,10000290,8.1,SUCCESS,0,0
  10000350,0x080,8,3,5,10000000,10000000,10000250,10000000,10000250,10000350,8.1,SUCCESS,0,0
  10000604,0x100,8,1,5,10000000,10000256,10000504,10000256,10000504,10000604,8.3,ARBITRATION_LOST_RETRY,1,0
  ```

  0x080 は 125 ビット（スタッフビット 17）で 250 µs。0x100 はインターミッション 3 ビット（6 µs）のあとに再送信され、124 ビットで 248 µs。

### 3.9 評価指標 [P④] [性能・ログ]
- **FR-070** 次の指標をログから算出できること。シミュレータ自身も終了時に集計して出力する。
  - 総送信レイテンシ Total_Latency = Rx_Process − Tx_Request
  - 送信待ち・調停遅延 Queueing_Delay = Tx_Start − Tx_Request
  - フレーム伝送時間 Tx_Duration = Tx_End − Tx_Start
  - バス負荷率 Bus_Load(%) = ΣTx_Duration / T_window × 100
- **FR-071** バス負荷率の計算ウィンドウ T_window は既定 100 ms とする。**[性能・ログ（例）] [既定]** バス負荷率の集計では、1フレームの Tx_Duration を1回だけ数える（受信ノードの数だけ重複して数えない）。インターミッションは Tx_Duration に含めない（[性能・ログ] の式どおり）。
- **FR-072** ジッターは、ID ごとに「連続する Tx_Start の間隔 − 送信周期」とし、最大・最小・標準偏差を出す。**[既定] [要確認 Q-7]**（[性能・ログ] の副題にあるが式がないため）
- **FR-073** 集計は、ID ごと、ノードごと、全体で出す。**[既定]**

## 5. 成功基準

- **SC-001** 同じ構成で2回実行したとき、ログが完全に一致する（再現性）。
- **SC-002** 同時の送信要求では、すべてのケースで ID の小さいフレームが先に送信される。
- **SC-003** 各フレームの Tx_Duration が、ビット列（スタッフビット込み）から手計算した値とビット単位で一致する。
- **SC-004** バス負荷率が100%未満の構成で10秒実行したとき、全フレームの送信回数が「(実行時間 − 通常動作開始時刻 − 初回オフセット) ÷ 周期」の切り上げと一致する。
- **SC-005** 16ノードの構成を読み込んで実行でき、17ノードの構成は拒否される。
- **SC-006** 性能目標は、実行環境が決まってから設定する。**[要確認 Q-8]**

## 付録A サンプル構成 **[既定]**

[図] は「各ECUは複数フレーム（ID／周期／DLC）を持つ」とだけ示しているため、動作確認用に次の構成を置く。ID は安全・制御系ほど小さくした。実際の値は既存資料で置き換える前提（Q-1）。

| 送信元 | ID | 内容（例） | 周期 | DLC | 最悪ビット長※ |
|---|---|---|---|---|---|
| ECU6 エアバッグ | 0x050 | エアバッグ状態 | 100 ms | 2 | 72 |
| ECU3 ABS/ブレーキ | 0x080 | 車輪速 | 10 ms | 8 | 132 |
| ECU3 ABS/ブレーキ | 0x081 | ブレーキ状態 | 20 ms | 4 | 92 |
| ECU1 エンジン制御 | 0x100 | エンジン回転数・車速 | 10 ms | 8 | 132 |
| ECU1 エンジン制御 | 0x101 | エンジン状態 | 100 ms | 8 | 132 |
| ECU2 トランスミッション | 0x120 | ギア位置 | 20 ms | 4 | 92 |
| ECU4 ボディ制御 | 0x300 | ドア・灯火状態 | 100 ms | 2 | 72 |
| ECU5 メータークラスタ | 0x400 | 表示状態 | 200 ms | 8 | 132 |

※ SOF〜EOF のビット長 44 + 8×DLC に、最悪のスタッフビット数 ⌊(34 + 8×DLC − 1) / 4⌋ を加えた値。インターミッションは含めない（FR-071）。この構成の最悪バス負荷率は約 7.8%（500 kbps）。
